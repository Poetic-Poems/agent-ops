# Summary

## What this project is

`agent-ops` is the operations home of the **Poetic autonomous agent pipelines**: a self-hosted, unattended system that selects, implements, and reviews pending work across `Poetic-Poems/poetic`, `Poetic-Poems/poetic-fiddle`, and `agent-ops` itself, raising mergeable pull requests for human review. It runs as scheduled containers (`supercronic` inside a Docker image), invoking the `claude` CLI as every pipeline stage's actual agent — a Co-Ordinator selects work, an Implementer builds it, a Reviewer checks it, and (above the default `human` trust level) an Approver can approve and land it, with an Enabler and Refiner handling stalled or under-specified items. A local dashboard (`dashboard/index.html`) gives the one operator, `warwickallen`, visibility into the fleet.

The codebase is almost entirely Bash (~26,600 lines across `lib/` (70 files), `scripts/` (~70 files), and the two cycle entry points `agent-cycle.sh` (9,920 lines) and `review-cycle.sh` (1,043 lines)) plus a handful of Perl scripts for the tech-debt register and one HTML/JS file for the dashboard. There is no package manager — dependencies are baked into a pinned Docker image. The project is 42 days old (451 commits, 2026-07-13 to 2026-08-23), 443 of them from one human identity, and moves extremely fast: dozens of merged PRs a week, a 94-item tech-debt register (76 resolved), and a 17,320-line as-built specification kept deliberately in sync with the code. It is also mid-flight on a deliberate strangler-rewrite into a monetised product ("Pullwright", `docs/ROADMAP.md`), with the current single-tenant, single-operator shape a known, tracked, interim state rather than an oversight.

## Overall assessment

This is an unusually mature codebase for its age, with genuine engineering discipline behind its size: clean quoting and command construction, a repo-wide shellcheck gate that passes clean, an as-built specification held to a hard "code and spec change together" rule that verification in this review confirmed actually holds, and — most tellingly — a demonstrated habit of *noticing and fixing its own defect classes* (a serial-subprocess-forking antipattern was found and re-swept six times across the tech-debt register; three of this review's own Medium findings were already self-filed as open tech debt in the 24–48 hours before this review ran). The 140-file, 52,000-line test suite tests real concurrency with real processes rather than mocks, and its "wiring" tests defend against exactly the kind of test/code drift that silently invalidates a suite.

Against that strength sits one finding that outweighs everything else in this report: every pipeline stage runs the `claude` CLI with `--dangerously-skip-permissions` and a live write-scoped GitHub token in its environment, while being fed verbatim, untrusted text from three confirmed-public GitHub repositories — with no "treat this as data, not instructions" framing anywhere in the prompts, and no network egress restriction. This is a real, externally-reachable path from an anonymous GitHub issue or comment to credential exfiltration or destructive repository actions, only partially bounded by GitHub's own self-approval and branch-protection rules (see F-SEC-01 / R-01). Everything else in this review is genuinely secondary by comparison.

The next most consequential issue is architectural rather than acute: `agent-cycle.sh`, the pipeline's actual cycle body, has grown a ~3,400-line undecomposed top-level flow that cannot be unit-tested the way the rest of the codebase's library functions are (F-CODE-01 / R-02) — a natural consequence of 42 days of fast, single-author iteration, and one the project's own roadmap already plans to address via a repository split, but worth tackling before it grows further. A `publish-dashboard.sh` clock-coupling gap already caused one real merge-queue incident (F-TEST-02 / R-03) and is the clearest concrete "this already bit someone" finding besides the security issue.

## Headline strengths

- A repo-wide `shellcheck` gate (250 tracked scripts) runs clean, matched by consistently disciplined bash style (`[[ ]]`, module-scoped naming, justified suppressions) [F-CODE].
- The tech-debt register (94 items, per-item file format, CI-validated) is used as intended — as a live, active queue, not an archive — and shows a genuine habit of re-auditing after a fix to catch the remaining instances of the same bug class [F-PERF, F-OPS].
- Concurrency-sensitive code (claim locks, ID reservation) is tested against real races with real processes, not mocks or sleeps [F-TEST].
- The as-built spec discipline CLAUDE.md mandates was independently verified, not just claimed: `render-config-table.sh --check` passes clean and three sampled `REVIEW-PIPELINE-SPEC.md` requirements matched the code verbatim [F-DOC].
- GitHub-facing retry/degradation handling (rate limits, secondary limits, crash-loop detection) is centralised, well-tested, and grounded in real prior incidents rather than designed in the abstract [F-OPS].

## Headline risks

- Every pipeline stage runs with unrestricted tool access and a live write-scoped token while processing verbatim untrusted text from public repositories, with no technical barrier against a prompt-injection-to-exfiltration path [F-SEC-01].
- `agent-cycle.sh`'s ~3,400-line undecomposed main flow is both the highest-stakes and least testable code in the repository [F-CODE-01, F-ARCH-01, F-ARCH-02].
- A already-materialised clock-coupling bug in `publish-dashboard.sh` dequeued a human-approved PR from the merge queue after the fact [F-TEST-02].
- Three observability gaps (a discarded GraphQL error, a misclassified missing-token state, an unobservable traceability check) each independently caused a real, multi-day-invisible incident, and are already self-filed as open tech debt [F-OPS-01, F-OPS-02, F-OPS-03].
- The dashboard's one real interactive surface (expandable rows, filterable cards) has no keyboard equivalent for most of its functionality [F-UX-01].

## Scope and method

This is the first `project-review` skill run against this repository (`reviews/` did not previously exist). The review covers all 13 checklist dimensions. Given the codebase's size (~27,000 lines of shell/Perl across `lib/`, `scripts/`, and the two entry points, plus ~52,000 lines of tests and a 17,320-line specification), full-dimension review work was parallelised across nine subagents, each assigned one or two dimensions, the shared project map (`worknotes/project-map.md`), and instructions to sample representatively rather than read exhaustively. Entry points (`agent-cycle.sh`, `review-cycle.sh`) and the most cross-referenced/highest-risk libraries (`lib/landing.sh`, `lib/merge-autonomy.sh`, `lib/approver*.sh`, `lib/claim.sh`, `lib/github-limit.sh`, `lib/handoff.sh`) were read closely; the remaining ~60 `lib/` files and ~65 `scripts/` files were sampled by relevance to each dimension. All 140 test files were inventoried; roughly a dozen were read and run directly.

Automated corroboration actually run in this environment: `scripts/lint-shell.sh` (shellcheck 0.10.0, matching CI's pinned version) — clean across all 248 tracked scripts; `perl scripts/td-check.pl` — the tech-debt register is internally consistent (94 items: 17 open, 76 resolved, 1 not-debt); `scripts/render-config-table.sh --check` — all generated documentation regions match `config.schema.json`; roughly a dozen `test/*.test.sh` files run directly against the host toolchain (not the intended Docker-image runner — this environment has no `docker`), all passing, several timed to identify runtime outliers; `gh repo view`/`gh pr list`/`gh issue list` against the live repository, confirming repository visibility and current open-PR/issue state.

**Not run:** the full test suite via `scripts/run-tests.sh` inside the project's own Docker image, as CI runs it (no `docker` in this environment; the script's own header explains why a host-side run is not equivalent — `jq` version drift between 1.6 and 1.7). Live browser-based accessibility auditing (e.g. axe) of `dashboard/index.html` (no browser tooling available; assessed by reading markup/CSS/JS instead). Git-history secret scanning was a targeted, not exhaustive, sweep of files most likely to carry one (`.env.example`, `config.json`, `claude-settings.json`, `cloud-init.yaml`) rather than a full-history tool run (no dedicated secret scanner available). No dimension was judged wholly inapplicable, though UX and DATA were judged proportionately light given the project's current single-operator, low-personal-data-footprint scope.
