Requirement 25a (spec'd in PR #256, issue #240) states that the
`closing-keyword` CI check "must also be listed in the repository ruleset's
required status checks — a repo setting, not a workflow file — so red blocks
the merge rather than merely reporting". The setting is now in place (the
`default` branch ruleset requires `closing-keyword`, pinned to the GitHub
Actions app, `integration_id` 15368), but a ruleset lives outside the
repository: no file in this repo changes when someone edits or recreates it,
so nothing — no CI job, no doctor check, no acceptance check — would notice
it drifting back to report-only.

This is exactly the gap PR #256's review fell into: the workflow existed and
went green, the ruleset silently did not require it, and only a human
reading the repo settings by hand caught the difference. The check would go
red on a non-conforming PR while the merge button stayed live, which reads
as enforced and is not — the same silent failure shape requirement 25a
itself exists to close, one level up.

Where: `scripts/doctor.sh` (the natural home — its remit is "a failure that
otherwise costs a cycle, or a night, to notice", and every GitHub call it
makes is a GET). Acceptance check 8m in
`docs/IMPLEMENTATION-PIPELINE-SPEC.md` (filed alongside this item) already
records the manual form of the verification — the `gh api` read and the
exact entry it must print — and names this item as the path to making it
deterministic; update 8m when this lands so the check stops being manual.

Suggested fix: a warn-level doctor check that reads
`gh api repos/<slug>/rulesets` for this repository, finds the active branch
ruleset targeting the default branch, and warns unless its
`required_status_checks` include `closing-keyword` with
`integration_id` 15368 — the same read acceptance check 8m spells out by
hand. Warn, not fail: the pipeline still runs without it, but the operator
should learn before the next non-conforming PR merges, not after.
