`_handoff_blocking_reviewers` (`lib/handoff.sh`) returns the login of every
account whose latest review is `CHANGES_REQUESTED`, unfiltered.
`confirm_review_requested` then POSTs those logins to
`repos/<slug>/pulls/<n>/requested_reviewers` and — correctly, per
TD-PPagop-26081402 — re-reads the pending list rather than trusting the
POST's exit status, reporting `failed` when a login it asked for is not
there afterwards.

Where the blocking reviewer is a GitHub App, that re-read can never come
back satisfied. GitHub's `requested_reviewers` field holds users and teams;
an App's bot identity is not addressable there. The POST returns **200** with
the pull request body — no error, no 422 — and the bot login is silently
absent from `requested_reviewers` on the very next read. The verification is
doing exactly what it was built to do; the thing it is verifying is not
achievable.

On this installation that is the ordinary case, not an edge one.
`pullwright-approver-poetic[bot]` is the account that submits
`CHANGES_REQUESTED` on this system's own pull requests, so every
`review-feedback` round ends with `confirm_review_requested` reporting
`failed`, a `warning` event, and `review_requested: failed` on `pr-ready`.

## Why it matters

It is a warning that is always wrong in the same way, which is the kind that
stops being read. The `pr-ready` field and the dashboard warning exist to
distinguish "the human was notified" from "the human was not" — the whole
point of TD-PPagop-26081402's fix. A signal that fires on every round
regardless of whether anybody was actually notified carries no information,
and the round where a *real* notification failure happens looks identical to
the eighty before it.

It also costs each round a wasted write and two extra API reads, and it
leads every stage that reads the prompt honestly — the Implementer on PR
\#713 did exactly this — into spending a comment explaining an anomaly that
is structural rather than particular.

Worth noting that the pull request is not actually invisible today: a
standing request against the human account (`Warwick-Allen`) is what puts
these pull requests in a queue somebody reads, and that request is placed by
a different path. So this is a bad signal rather than a lost notification —
but which of the two it is, is currently indistinguishable from the log.

## What to do

Decide what "notified" means when the blocker is an App, and make the report
say that instead of `failed`. Two candidates:

- Filter App/bot logins out of `_handoff_blocking_reviewers`' output for
  *requesting* purposes only (it must stay unfiltered for deciding whether a
  block exists), and fall through to `ensure_human_reviewer`'s target — the
  human whose queue actually matters. `confirm_review_requested` then reports
  `already`/`requested` truthfully about a request that can exist.
- Or keep asking, and add a third outcome — `unrequestable`, say — for a
  blocking login GitHub will not accept, distinct from `failed`, carried on
  `pr-ready` and rendered differently on the dashboard.

Either way `prompts/implementer.md` and `prompts/reviewer.md` should stop
telling the stage to POST a login that cannot land, and requirement 31b
should state what the pipeline does when the blocking reviewer is an App.

Noticed while reviewing PR #713 (agent-ops#687), where both the Implementer
and this Reviewer independently made the call, got a 200, and found the
login absent from `reviewRequests` immediately afterwards.
