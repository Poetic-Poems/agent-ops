title: "escalation-failed reconcile comment has no dedup across retries — identical Script comments accumulate on the item's thread"

**What.** `escalation_thread_reconcile` (lib/enabler.sh, agent-ops#815) posts "No escalation issue was filed for this item: the attempt itself failed…" on a needs-refinement item's thread when an `escalate` verdict cannot be filed. Requirement 35a deliberately does not count `escalation-failed` as an examination, so the item is retried once its claim expires — and on the sub-case where the verdict simply carried no filable title/body, `gh` itself is healthy, so every retry posts another identical correcting comment with no dedup. (The other sub-case, `gh issue create` failing, is self-limiting: the follow-up `gh issue comment` almost certainly fails too and is swallowed as a warning.)

**Why it matters.** The thread is one a human is expected to read — it is the escalation-context thread — and an Enabler that repeatedly returns an `escalate` verdict with an empty `issue.body` turns it into a pile of identical Script comments, burying the signal the comment exists to carry.

**Where.** `escalation_thread_reconcile` and its caller's `escalation-failed` branch, lib/enabler.sh; the retry behaviour is requirement 35a's, docs/IMPLEMENTATION-PIPELINE-SPEC.md.

**Suggested fix.** Before posting the `escalation-failed` body, check whether an identical Script comment (matched on the fixed prose plus the `actor=script` pipeline marker, ignoring the cycle id) is already the thread's most recent Script comment, and skip the post if so — or key the dedup on any prior `escalation-failed` reconcile for the same item since its `blocked_ts`. The Reviewer on PR #819 identified this and deliberately left it: the right dedup key is a judgement call, and guessing wrong there would be worse than the visible noise. Whoever picks this up should make that call explicitly and pin it with a test alongside the existing reconcile scenarios in test/enabler-verdicts.test.sh.
