title: The Refiner cannot proactively refine tech-debt, project-review or implementation-plan items
status: open
filed: 2026-08-08
---

The Refiner's candidate gathering (`refiner_candidate_items` in
`lib/refinement.sh`, requirement 39a) reaches only the sources
`agent-cycle.sh` already pre-fetches as structured JSON before the
Co-Ordinator runs: `findings` (`security`/`code-quality`), `review_feedback`,
`abandoned_drafts`, `merge_conflicts`, `register_hygiene` and `issues`. A
`tech-debt`, `project-review` or `implementation-plan` item is never a
candidate, whatever `refinement_policy` says about it — there is no
pre-fetched array to draw one from, because the Co-Ordinator reads those three
sources live, with its own tool access, rather than being handed them as JSON
(tech-debt rows from `TECH-DEBT.md` directly, review recommendations from the
review folders, plan tasks from `implementation_plan_path`).

This matters because `tech-debt` is exactly the other source the 2026-08-07
pipeline-flow review's WI-11 recommendation named as usually needing
refinement, alongside `issues` — a tech-debt row as terse as "tidy up the sync
script" is the same under-specification shape an issue can have, and today it
can only ever be reported by the Co-Ordinator's own `needs_refinement` and
resolved by the (Opus) Enabler's existing requirement 36b duty, never by the
cheap Refiner. Setting `refinement_policy.tech-debt` to `"required"` or
`"preferred"` is accepted by the schema and shapes the Co-Ordinator's ranking
correctly, but produces no engagement to act on it — an installation that sets
it will simply see its tech-debt backlog wait for the ordinary blocked/Enabler
path, with no proactive refinement ever happening.

Suggested fix: give the Refiner a narrow read path for these three sources,
analogous to what the Co-Ordinator already does but scoped down —
`TECH-DEBT.md`'s `open`/`in-progress` rows via
`scripts/get-tech-debt-record.pl`, the current review-cycle's recommendation
files, and the plan document at each repo's `implementation_plan_path` — and
fold their candidates into `refiner_candidate_items`'s input the way `issues`
already arrives, rather than growing the Refiner into a second reader of
`TECH-DEBT.md` with independent parsing logic. Whether this needs a new
gatherer script (mirroring `scripts/gather-issues.sh`) or can reuse
`scripts/get-tech-debt-record.pl` directly against every open row is worth
deciding against the two other sources at the same time, since all three
share the same "no pre-fetched array" gap.
