Requirement 3s's **Superseded** case (a newer Dependabot PR already covers
the same dependency) records the older bump in `voided`, carrying
`superseded_evidence`. Until TD-PPagop-26080901, recording that void also
closed the pull request, through requirement 34k's ordinary act-on-void
path: the item's `pr-<n>-conflict-<head-sha>` ref was all that path needed.

TD-PPagop-26080901 excluded that entire shape from 34k's close, because the
same shape is also minted for a live, unconflicted PR of ours whose conflict
merely resolved — and closing *that* one destroyed pull request #264 along
with a human `CHANGES_REQUESTED` review round. The exclusion is on the id
shape, not on the reason for the void, so it necessarily disabled the
supersession auto-close too. That was the correct trade at the time
(TD-PPagop-26080901's own text weighs it: a distinct id shape "would remove
the ambiguity at the source, but it is the larger change"), and the spec and
`prompts/coordinator.md` were updated in the same pull request to state the
new behaviour. This item records what the trade cost.

The cost: a superseded Dependabot bump is still voided — it stops being
offered as a candidate every cycle, which was the larger half of the problem
— but it now stays open on GitHub until a human closes it by hand.
Dependabot itself will not: it closes a bump it supersedes only when it
raises the replacement against the same base, which is exactly the case
`superseded_by` exists to catch because Dependabot did *not*. So these
accumulate, one open obsolete PR per superseded bump, in the repository's own
pull request list — the same "visible to every human and every tool that
reads GitHub rather than this pipeline's log" complaint that motivated
requirement 34k in the first place (issue #240).

## Suggested fix

Mint a distinct id shape for the two cases, so the close decision can be
taken on the id alone without the ambiguity. This is the "larger change"
TD-PPagop-26080901 identified and deferred: requirements 3g and 23 mint the
id, requirement 34d's finishing-source corroboration rule reads it, and
`lib/work-gone.sh`'s `WORK_GONE_PR_RE` is shared with requirement 34i's
clearance rule and `lib/preflight.sh` — where treating all the `pr-<n>-`
shapes alike is correct and must stay that way. Once the two are
distinguishable, the supersession shape returns to 34k's close branch and the
conflict-resolved shape stays excluded.

A narrower alternative, if the id-shape split proves too invasive: give the
Co-Ordinator's superseded case its own explicit close, separate from the
act-on-void path, so requirement 34k keeps its blanket exclusion. That
localises the change to requirement 3s but adds the second closing mechanism
requirement 34k's design note deliberately avoided.

Note that whichever route is taken, `pr-<n>-conflict-<head-sha>` currently
has no actioned signal at all and so never retires from the void extract —
TD-PPagop-26081303 covers that, and the two interact: restoring a close for
the supersession shape also restores its retirement.
