title: Void shapes with no actioned signal never retire, so the extract still grows without bound

Requirement 34n retires a void entry once it is both actioned and old, and
"actioned" is defined by the only two signals that exist: requirement 34k's
`void-object-closed` (recorded by `scripts/close-void-github-items.sh`, which
acts on the bare-issue-number and `pr-<n>-…` shapes and no others) and a
tech-debt register row reading `resolved`/`not-debt`. Every other item id the
pipeline can void has no actioned signal defined for it at all, so it never
retires and the extract keeps the same unbounded growth curve underneath the
bounded part:

- `review-<date>-R-<n>` — a project-review recommendation ref (requirement 15);
- an implementation-plan task id (`W10-breach-handling`);
- `dependabot-alert-<n>` and `code-scanning-alert-<n>`
  (`scripts/gather-findings.sh`);
- `register-hygiene-<12 hex>` (`scripts/gather-register-hygiene.sh`);
- `failed-run-<workflow basename>`;
- a void naming no repo at all — the hand-appended form requirement 34c
  allows, which can match no actioned pair by construction.

`register-hygiene-<hash>` matters most, because its id is minted per
occurrence rather than naming a durable object: the hash is scoped to the
register state that produced it, so no two ever coalesce and every one that
is voided leaves a permanently unretirable entry behind. The alert refs come
next, one per alert ever filed; `failed-run-` is bounded by the repo's
workflow count and a review ref by the weekly review's own numbering, so
those grow slowly rather than not at all. Requirement
34n's own text states this limit, so the behaviour is documented and
deliberate — what is not yet decided is what closes it.

## Suggested direction

Two candidate rules, and the choice between them is the actual work:

- an **age-only** retirement at a longer threshold (a multiple of
  `void_retire_after_days`, or its own config key) for shapes that have no
  actioned signal, on the argument that a void nothing can ever action is
  precisely the one that will never earn its exit; or
- an **actioned signal per shape** — a merged pull request for a review ref
  and a plan task (requirement 34i already reads both, via
  `scripts/gather-review-status.sh` and `scripts/gather-plan-status.sh`, for
  the blocked set), and the alert's own state for an alert ref — leaving only
  the per-occurrence shapes, which may be better served by not recording
  void state against a one-shot id in the first place.

Either way the acceptance shape is requirement 34n's own: a test in
`test/cycle-state.test.sh` pinning that an entry of each named shape retires
under the new rule and that nothing else changes about what counts as void.
