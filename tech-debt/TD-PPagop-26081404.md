TD-PPagop-26081305 gave a node that cannot read a pull request's required
checks its own `unknown` verdict from `review_gate_verdict`
(`lib/review-gate.sh`), so `agent-cycle.sh`'s `rev_status == "ready"` block
now logs a distinct node-level `warning` — naming the node and what could not
be read — alongside the `attempt-failed` handback it still records for the
item (the handoff stays refused; an unread required-check list is never
evidence of "nothing wrong").

That fixes attribution for a single occurrence, but not for a run of them.
`gh` degraded enough to fail this read does not usually fail it once: a node
past a rate limit, or fighting a transient auth problem, is typically wrong
for several consecutive items across a cycle (or several cycles), and each
one still earns its own `warning` plus its own `attempt-failed`. A human or
an Enabler scanning the log sees N node-level warnings rather than one loud
"this node has failed N times in a row", which is the shape that would
actually prompt someone to go look at the node instead of the pull requests.

Suggested fix, from TD-PPagop-26081305's own body: a consecutive-failure
counter for this specific gate, keyed on the node, that only starts logging
past a small threshold and does so as a single escalating event rather than
one per item — the crash-loop machinery (requirement 9e,
`lib/crash-loop.sh`) is the existing precedent for this shape in this repo,
and is worth checking first for whether its counter can be reused rather than
duplicated.

This is explicitly a follow-up, not a regression: TD-PPagop-26081305's own
acceptance criterion listed "consecutive-failure escalation" as optional and
out of scope for that item, and its pull request lands without it.
