`maybe_run_enabler` in `agent-cycle.sh` decides what each Enabler verdict
records — `unblocked`, `void`, `still-blocked`, `escalate`, and the two
refusals that degrade a verdict rather than honouring it — and no test in
`test/` executes any of it. `test/enabler-eligibility.test.sh` only feeds
`enabler-examined` events in as log fixtures to exercise the eligibility
extract; nothing calls the function, so nothing asserts which event a verdict
produces or which `outcome` travels on it.

Two outcomes are affected today, both of them the failure paths rather than
the happy ones:

- `void-refused` — requirement 34d's guard refusing the Enabler's own `void`
  (added by PR #258, issue #243). `grep -rn 'void-refused' test/` is empty.
- `refinement-refused` — requirement 36b's equivalent for a refused
  refinement. Untested the same way, and untested before #243.

This matters because a refusal is the path that keeps a wrong permanent
verdict from being recorded, and its whole value is in what it writes instead:
an `attempt-failed` that leaves the item blocked-and-clearable, plus an
`enabler-examined` whose outcome is `void-refused` and *not*
`escalation-failed`, since the latter is exempted from the ordinary
examination accounting (requirement 36a). A silent regression there would put
the item back where 34d exists to keep it out of, and every event in the log
would still read like an ordinary examination.

PR #258 originally extended acceptance check 8c to require the `void-refused`
assertion; the clause was trimmed back there because the specs are as-built
and no such test exists. Restore it — and add the `refinement-refused`
equivalent to requirement 36b's own check — when this item lands.

Where: `agent-cycle.sh` (`maybe_run_enabler`, the `void` and refinement
branches of its verdict `case`), acceptance check 8c in
`docs/IMPLEMENTATION-PIPELINE-SPEC.md`, and a new `test/enabler-verdicts.test.sh`.

Suggested fix: the harness is the work, not the assertions. The stage-level
tests (`test/stage-*.test.sh`) already drive `agent-cycle.sh` against a stubbed
`claude`, so the cheapest route is probably to follow that pattern with a
stubbed Enabler response per verdict and assert the events the cycle log
gains. If that proves too heavy, the alternative is to lift the verdict switch
into `lib/` the way `lib/refinement.sh` already holds the refinement rules, and
unit-test it there — which would also stop the `void` branch and the
Implementer's branch (`agent-cycle.sh`, around the `impl_status == "void"`
check) carrying two hand-kept copies of the same refuse-and-degrade shape.
