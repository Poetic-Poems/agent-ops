The dashboard's back-pressure card states its own invariant in a comment
(`dashboard/index.html`, the `humanQueueN` block): it "mirrors
`agent-cycle.sh`'s own four-part sum (requirement 2.2) rather than
recomputing a different one", because "a card that reports a different
figure from the gate it depicts is worse than no card".

Requirement 2.2's exclusion is level-aware (D18 WI-6). For a repository whose
`merge_autonomy_effective_level` (requirement 2.3b) ranks
`agent-merges-routine` or above, `agent-cycle.sh` counts **every** ready pull
request toward `max_open_agent_prs`, `CHANGES_REQUESTED` or not — above that
level there is no human queue for a ready pull request to be parked in, so
the exclusion's premise no longer holds.

The card applies no such test. Its computation is unconditional:

```js
var humanQueueN = openPrs.filter(function (p) {
  return !p.isDraft && p.review_decision !== "CHANGES_REQUESTED";
}).length;
```

So at `agent-merges-routine` and above the card excludes from its sum exactly
the pull requests the gate counts, and reports them under "waiting on human"
— a queue that, at that level, nothing is waiting in. The gauge reads low
against a cap that is closer to tripping than it appears, and the tooltip's
"plus N waiting on human" names an actor with no next action.

## Why it matters

The card exists to let an operator see why the fleet stood down. At
`merge_autonomy: human` — this installation's setting when the card was
written — it is correct, which is why the divergence has gone unnoticed. It
becomes wrong precisely at the level the pipeline is being moved towards, and
it is wrong in the reassuring direction: the gauge under-reports pressure.

`docs/DASHBOARD-SPEC.md` (the back-pressure card's requirement, and the
`backpressure-claim-scope.json` fixture note) describes the current,
non-level-aware behaviour accurately, so this is a behaviour gap rather than
a spec/code mismatch — the spec would need the same edit as the code.

## What a fix needs

The effective level is per repository, and the card sums `openPrs` across
every configured repo in one pass, so the fix is not local to the filter:
`scripts/publish-dashboard.sh` would have to publish each repo's
`merge_autonomy_effective_level` (requirement 2.3b) alongside its pull
requests, and the card would have to partition by repo before applying the
exclusion — the same per-repository judgement `agent-cycle.sh` already makes
inside its own per-repo loop.

Noticed during the review round of PR #748 (the #679 vocabulary sweep), which
reworded the *prose* asserting an unconditional human queue at the
`agent-cycle.sh` and `lib/handoff.sh` sites but correctly left the dashboard's
own copy alone, that prose being an accurate description of what this card
still computes.
