Noticed while working #822 (the model-tier floor, requirement 1c).

## What

`docs/IMPLEMENTATION-PIPELINE-SPEC.md` requirement 1a ("Model id resolution")
names the keys `agent-cycle.sh` resolves through `resolve_model_id` before
the lock: "`coordinator_model`, `implementer_model_default`,
`implementer_model_trivial`, `reviewer_model_default`,
`reviewer_model_complex`, `enabler_model`". The code resolves four more that
this list omits: `refiner_model` (`agent-cycle.sh:523`, pre-existing) and
`approver_model_default`/`approver_model_complex`/`approver_model_critical`
(`agent-cycle.sh:421,424,427`, pre-existing). None of these four are
unresolved in practice — the omission is the prose falling behind the code
it describes, not a functional gap — but it means a reader of requirement 1a
alone would not know four of the fleet's ten model keys go through the same
provider-qualifier check the other six do.

`scripts/doctor.sh`'s own "Models" section resolution list had the same gap
for `refiner_model` specifically; #822 fixed that one (it sits beside the
model-tier ladder that issue added, which needs `refiner_model` resolved to
check it). The `approver_model_*` three were never in scope for #822 and are
untouched.

## Why it matters

Low severity — this is a documentation-completeness gap, not a behavioural
one. But requirement 1a is the kind of paragraph an installer reads to
understand what the Script validates before it will start a cycle, and right
now it undersells that by 40%.

## What it would take

Add `refiner_model`, `approver_model_default`, `approver_model_complex` and
`approver_model_critical` to requirement 1a's enumeration in
`docs/IMPLEMENTATION-PIPELINE-SPEC.md`. No code change — `agent-cycle.sh`
already resolves all four; this is a spec-text-only fix.
