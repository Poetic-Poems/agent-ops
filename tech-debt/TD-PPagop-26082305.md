Issue #670 records two independent defects behind the same fleet incident.
The first — the own-label read-back measuring its grace period against wall
clock rather than the union-log snapshot's own horizon — is fixed by PR #700,
whose `Closes #670` retires the issue and with it the only record of the
second. This item is that second defect, carried forward.

## What happens

poetic-1's Refiner blocked agent-ops#597 and #598 as `needs-refinement` with
the detail *"Already fully refined by the Enabler … nothing has changed
since, so a second specification is not mine to write"*, and an
`unblock_condition` reading *"Nothing on the specification side … The only
remaining gap is that a human must remove the hand-applied
`needs-refinement` label"*.

At the moment that block was written the label was not on the issue. The
Script added it three seconds later — 2026-08-21T07:41:26Z — as requirement
34e's projection of that very block. So the block's stated unblock condition
is *"a human must remove the label this block is about to create"*: a
deadlock the pipeline manufactures for itself and then cannot exit under its
own power. Both items needed a hand on a label to escape (escalations #660
and #666).

## Why it still matters after #700

PR #700 breaks the loop from the other side: with the grace period measured
against the snapshot horizon, a peer's own label write is no longer
misattributed to a human, so the item stops cycling. That is a fix to the
*attribution*, not to the block. A Refiner verdict whose unblock condition
only a human can satisfy is still reachable by any other route that puts a
`needs-refinement` label on an already-refined item, and it still costs a
human engagement each time. #670's own words: *"Either fix alone breaks the
loop; both are worth having, because they fail in different directions."*

## Suggested fix

A Refiner that finds an item already adequately specified has found the item
**ready**, not under-specified. That outcome needs to be something other than
`needs-refinement`: the item should proceed to selection, or at minimum block
on a kind whose unblock condition the pipeline can satisfy itself. Whichever
way it lands, the invariant worth stating in
`docs/IMPLEMENTATION-PIPELINE-SPEC.md` is that no stage may write a block
whose `unblock_condition` names, as the only remaining gap, a state that
same block is itself about to create.

- `agent-cycle.sh`, requirement 34e — the block-to-label projection that
