Before agent-ops#654 (PR #715), `prompts/implementer.md` named the label to
apply literally — "Label it `pr_label` (`autonomous-agent`)" — so the
Implementer always had a value to apply, whatever the work order carried.
That literal is the Poetic-specific the issue set out to remove, and the
prompt now reads "Label it `pr_label` (received in the work order)": the
value arrives on the work order, threaded from `config.json` through the
Co-Ordinator's runtime input, or — since PR #715's review — composed
directly by `fallback_select_candidate` on the mechanical-selection path
(requirement 3v).

Both of those producers are now correct, but only one of them is the
Script. The model path depends on the Co-Ordinator actually copying the
runtime input's `pr_label` into each candidate, which is a prompt
instruction like any other. Nothing between the Co-Ordinator's final message
and the Implementer's first tool call checks that the field is there: the
claim loop stamps `branch` onto the winning candidate
(`agent-cycle.sh:8983`, requirement 17a) and passes everything else through
untouched, and no requirement validates the work order's shape beyond
requirement 17f's refinement traceability.

## Why it matters

The failure is silent and it is not self-correcting. `pr_label` is not
decoration: it is how *every* gatherer finds this system's own pull requests
again — `gather-review-feedback.sh`, `gather-abandoned-drafts.sh`,
`gather-merge-conflicts.sh`, `gather-dequeued.sh`,
`gather-human-visibility-hygiene.sh`, `scripts/sweep-closed-issues.sh` and
`lib/merge-budget.sh` all list by it — and how requirement 2.2's
back-pressure counts them. An Implementer that applies no label opens a
draft that looks, to the next cycle, like a stranger's pull request: it is
never gathered as an abandoned draft, never counted against
`max_open_agent_prs`, and its item's claim outlives the cycle with nothing
pointing back at it. `scripts/sweep-orphan-branches.sh` already treats
exactly this state as a defect worth warning about in its own recovery path
("recovered without the $pr_label label — the abandoned-drafts source cannot
see it until someone adds the label"), which is the same condition arrived
at by a different route.

A missing `model` field fails loudly at the next launch; a missing
`pr_label` costs one orphaned pull request per occurrence and says nothing.

## Where

- `agent-cycle.sh` — the claim loop's `claimed_json="$(jq -c --arg b
  "$c_branch" '. + {branch: $b}' <<<"$cand")"` (line 8983), the one point
  every work order passes through, whichever producer composed it.
- `prompts/coordinator.md` — "What you receive at invocation" (the
  runtime input's `pr_label`) and the "Output" work-order template.
- `prompts/implementer.md` — the work-order example and step 4's "Label it
  `pr_label` (received in the work order)".
- `docs/IMPLEMENTATION-PIPELINE-SPEC.md` — requirements 20, 23 and 3v.

## Suggested fix

Stamp the configured value onto the winning candidate in the claim loop,
alongside `branch`, and let it override whatever the candidate carried:

```sh
claimed_json="$(jq -c --arg b "$c_branch" --arg pl "$pr_label" \
  '. + {branch: $b, pr_label: $pl}' <<<"$cand")"
```

There is exactly one correct value for this field — `config.json`'s, which
is the string every gatherer greps for — so a model retyping it is a copy
opportunity with no upside, and the Script already owns `branch` on the same
object for the same reason. The Co-Ordinator's own copy is then belt and
braces rather than the load-bearing path, and requirements 20/23 would say
so.

Noticed by the Reviewer stage while reviewing PR #715
(https://github.com/Poetic-Poems/agent-ops/pull/715), which introduces the
work-order field; the guaranteed-missing half of the gap (the mechanical
fallback composing no `pr_label` at all) was fixed in that pull request,
and this is the residual, which is a question about where authority for the
value should live rather than a defect in the change itself.
