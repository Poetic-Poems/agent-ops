PR #268 delivers stages 1 and 2 of issue #248 — finish-then-continue
(`lib/chain.sh`, `agent-cycle.sh`'s chain gate, requirement 39) and the
sub-hourly cycle interval (`schedule.cycle_interval_minutes`, requirement 2.6's
crontab) — and closes the issue. Three of the issue's own acceptance items do
not travel with it.

**The two metrics cannot be checked before deployment, and nothing asks for
them afterwards.** Acceptance 4 is "median claimed time under 20 min measured
across fleet with >1 active node" and acceptance 5 is "no increase in
duplicate-work incidents relative to before this feature". Both are properties
of the running fleet, not of the diff, so no test or CI job can stand in for
them. The `Closes #248` keyword retires the only place they are written down
the moment the PR merges, which leaves the change's stated success criteria
unowned rather than unmet.

The data to answer both already exists in the event stream: `selection` events
carry `race_losses` (requirement 17d, new in the same PR) and every claim
failure logs `claim-lost` with its `cause`, so acceptance 5 is a ratio over the
union log rather than new instrumentation. Acceptance 4 needs the gap between
an item first appearing in a gathered source and the `selection` that claims
it, which is not currently recorded as a pair.

**Stage 3 loses its record too.** The issue defers event-driven dispatch —
GitHub webhooks, or a poller on the state repo, waking an idle node when a
source-relevant event lands — to Phase 2, gated on WI-2's PR-level claim
exclusion. `docs/ROADMAP.md`'s Phase 2 section does not name it, so once #248
closes the only description of stage 3 is in a closed issue's body.

There is also a cost the change makes and does not measure, which D14 in
`docs/ROADMAP.md` asks to be a recorded decision rather than a surprise on a
bill. `chain_sources_remain` counts enabled source *categories*, not items, and
back-pressure narrows `.sources` to the three finishing sources rather than
emptying it (`agent-cycle.sh`, the `ordered_repos_json` narrowing), so the
"sources remain" half of the gate is non-zero in essentially every reachable
state and `max_chained_cycles` is the only bound that fires in practice. A
productive cycle raises a pull request, which moves the no-op fingerprint, so
each chained cycle pays a full Co-Ordinator run rather than short-circuiting on
`lib/noop-skip.sh` — at the default of 3, two extra Co-Ordinator calls per
productive cycle whether or not anything was left to pick up.

Where: `lib/chain.sh`, `agent-cycle.sh` (the chain gate and the `race_losses`
counter), requirements 39 and 17d in `docs/IMPLEMENTATION-PIPELINE-SPEC.md`,
`docs/ROADMAP.md` (Phase 2), and issue #248.

Suggested fix: three separable pieces, in increasing size.

1. Record stage 3 where it will still be read — a Phase 2 line in
   `docs/ROADMAP.md`, or a fresh issue carrying the deferred text — before
   #248 closes.
2. Answer acceptance 5 from the union log as it stands: the rate of
   `claim-lost` with `cause: "held"` per selection, before and after this
   change, which needs no new events.
3. Answer acceptance 4, which does need a new one: the timestamp at which an
   item first became visible in a gathered source, so the interval to its
   `selection` is computable. That is the piece worth designing rather than
   bolting on, since "first visible" has to mean the same thing across
   sources that are gathered on very different cadences.
