Noticed while reviewing PR #699 (requirement 2.0b, agent-ops#691).

Requirement 2.0b detects a rejected GitHub credential before the Co-Ordinator
runs, and escalates it through `create_escalation_issue` — the same
duplicate-guarded route requirement 1c's usage-limit freeze and requirement
2.7's crash loop use. That route reaches GitHub with `GH_TOKEN`: `gh issue
list` for the dedup read, `gh issue create` for the filing. Both authenticate
with the credential 2.0b has just established GitHub rejects, so both answer
`HTTP 401: Bad credentials`, `create_escalation_issue` returns non-zero, and
the block logs a `warning` and stands down. Confirmed live against real
GitHub while reviewing #699, not inferred: an invalid `GH_TOKEN` 401s on
`gh api rate_limit` and on `gh issue list` alike.

For 1c and 2.7 the failed-filing path is a genuine exception — their triggers
(a Claude usage limit, a deterministic crash) leave GitHub reachable. For
2.0b it is the expected path, every cycle, for as long as the token stays
dead.

## Why it matters

This is the difference between requirement 2.0b's third acceptance criterion
being met in code and being met in effect. The check stops the spend — the
~$5–10/node/day agent-ops#691 was actually about — and that half works. But
the escalation half does not reach anyone: every escalation route in this
repository terminates in a GitHub issue, and there is no out-of-band channel
anywhere in the tree (no webhook, SMTP, or push target). A node whose
credential dies therefore tells nobody outside itself. Its remaining signals
are the local `stand-down` event in `state_dir/log.jsonl` and a dashboard
which, for the same reason, degrades to "showing last local state only" —
so the failure is visible only to someone who already suspects it and goes
looking at that node.

The same gap covers any future escalation whose own trigger is "GitHub is
not answering this node", not just 2.0b.

## Where

- `agent-cycle.sh`, requirement 2.0b's block (the `create_escalation_issue`
  call and its `warning` fallback).
- `create_escalation_issue` in `agent-cycle.sh` — the shared route, used by
  requirements 1c, 2.7 and 2.0b.
- `docs/IMPLEMENTATION-PIPELINE-SPEC.md` — requirement 2.0b, and the Gotchas
  row PR #699 added recording this asymmetry.

## Suggested fix

One out-of-band notification channel, configured per node and used by
whichever escalations cannot assume GitHub is reachable. The cheapest shape
that would have closed agent-ops#691's three-hour window is a single
optional config key holding a webhook URL (or an `smtp_*` group), POSTed to
on the paths where `create_escalation_issue` fails, carrying the same
`reason` and `detail` the `stand-down` event already has. It must be
credential-independent of `GH_TOKEN` — that is the whole point — and must
fail silently rather than aborting a cycle when unset, so an installation
that does not want one is unaffected.

Worth deciding at the same time whether `crash_loop_repo` escalations should
fall back to it generally, or only the routes whose trigger implies GitHub
itself is unavailable.
