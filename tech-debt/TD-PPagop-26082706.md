Noticed reviewing agent-ops#828, whose own standing open question is the
concrete instance.

## What

Requirement 8f's gate is `landing_open_question_hit` (`lib/landing.sh:1905`).
It reads the `open-question` label off the pull request, fresh from GitHub,
and nothing else — deliberately never a log join, so that a human's removal of
the label is seen the moment it happens. The label is therefore the *whole* of
the hold: no label, no gate.

`labels_catalogue` (`lib/labels.sh:118`) has carried `open-question`
unconditionally in its `target` role since `ea552db` (#776) landed on
2026-08-24, and `labels_ensure` creates every catalogue label a repository is
missing on each sweep. Three days later the label still does not exist in
`Poetic-Poems/agent-ops`: `gh label list -R Poetic-Poems/agent-ops --limit 200`
returns 25 labels and `open-question` is not one of them, while every other
catalogue label for the `target` role — `refined`, `needs-refinement`,
`blocked:needs-refinement`, `unvoided`, `obsolete`, `enabler-escalation`, the
three `complexity:*` — is present.

The observable consequence is on agent-ops#828. Its Reviewer round of cycle
`20260826T165700Z-poetic-1-493806` ended `ready` carrying an `open_questions`
entry (issue comment 5429786608, still unanswered). The pull request's full
timeline carries no `labeled` or `unlabeled` event for `open-question` at any
point, and its current labels are `autonomous-agent` and `complexity:high`.
So the question is recorded in an `open-question-raised` log event and stated
in a PR comment, and neither is something any gate reads.

`landing_open_question_label_project`'s own contract anticipates the
missing-label case — it returns `failed` for "a repo where the label was never
created", on the reasoning that "losing the label costs a filter, losing the
gate would cost the hold". With `landing_open_question_hit` reading nothing but
the label, losing the label *is* losing the hold, so that reasoning does not
hold for this failure mode.

Why the sweep has not created it in three days is the undiagnosed part. The
candidates worth ruling out, in rough order of likelihood:

- `labels_ensure_role` is reached for a repository only on some path that
  agent-ops has not taken since #776 merged (it is unset in `config.json`, so
  `labels_ensure_interval_hours` takes its `24` default; the stamp is per
  repository under `state_dir`).
- `_labels_create_one`'s `POST /repos/<slug>/labels` is being refused for this
  one label and the refusal is swallowed — it prints `failed` and
  `labels_ensure` returns 0 regardless, which is by design ("no caller may
  treat it as fatal") but means a persistently failing create is invisible.
- The label was created and then deleted by hand; there is no `unlabeled`
  event on #828 to suggest this, but a repository-level label deletion leaves
  no trace on a pull request that never carried it.

## Why it matters

Medium. The exposure is bounded today because `merge_autonomy` is
`agent-approves` on this installation, so a human still performs the merge and
has the chance to read the thread. But:

- The gate is what requirement 8f promises, and it is not operating. At
  `agent-merges-routine` or above — a level this roadmap is heading toward —
  a pull request carrying an unsettled open question would land unattended,
  which is precisely the outcome #668 built the gate to prevent.
- Neither of the two `escalation_autonomy` resolutions fires either, because
  both hang off the gate hitting. This installation is `adjudicate-first`, so
  the one bounded adjudication pass that would have *answered* the question
  never runs.
- The label is also the human-visible marker. A maintainer scanning open pull
  requests sees nothing distinguishing #828 from one with no question at all.

## What it would take

Two separable pieces.

1. **Diagnose and fix the sweep.** Establish which of the three candidates
   above is the cause and repair it. If it is a swallowed create failure, the
   fix is observability rather than behaviour: `labels_ensure` already prints
   `failed<TAB>name` lines for exactly this, so the question is whether the
   caller logs them and whether anything surfaces a label that has failed to
   create on every sweep for days. `scripts/doctor.sh` already warns per
   repository about a missing `unvoid_label`; the same check generalised over
   the whole catalogue would have caught this on the first run after #776.

2. **Decide whether the gate should read only the label.** The
   read-fresh-never-join design is deliberate and correct for the *release*
   direction — a human taking the label off must release the hold immediately,
   which a log join could not honour. It is the *hold* direction that has no
   backstop: an `open-question-raised` event with no later settlement and no
   label is currently indistinguishable, to the gate, from no question at all.
   A fallback that holds when the log says a question was raised and the label
   could not be projected would close this, at the cost of the release
   direction needing a matching log-side act. That is a design trade-off for
   whoever owns requirement 8f, not a mechanical fix, which is why this is
   filed rather than patched.

## Diagnosis (appended 2026-08-28, reviewing agent-ops#887)

The undiagnosed part above is candidate 2 — a swallowed create failure — and
the specific reason was the label's **description length**. GitHub caps a label
description at 100 characters. `labels_catalogue`'s `open-question` description
was 148:

> Projected by the Reviewer: an open question about the work order or its scope
> blocks unattended landing until adjudicated or a human acts (D18 #668)

so `POST /repos/<slug>/labels` rejected the create outright. `_labels_create_one`
then re-lists to tell a peer node's race apart from a genuine failure, and in a
repository where a human has since made the label by hand it finds the name
present and prints `present` — not `failed` — which is why even the `failed`
lines the record hoped to surface were never emitted here.

`obsolete`'s description was the same 148 characters, so it was the second entry
affected.

The evidence across the three configured repositories, all gathered 2026-08-28:

- Every catalogue entry whose description is 100 characters or fewer exists
  with its description intact. `blocked:needs-refinement`, at 93, is present in
  all three.
- `open-question` is absent outright from `Poetic-Poems/poetic` and
  `Poetic-Poems/poetic-fiddle`, while every other `target`-role entry is
  present in both.
- `obsolete` exists in all three with an **empty** description — hand-created,
  and create-only ensure never revisits an existing label.
- The `open-question` label that now exists in `Poetic-Poems/agent-ops` carries
  colour `e7c6c4`, not the catalogue's `d4c5f9`, and an empty description, so it
  was not created by `labels_ensure` either.
- No label in any of the three repositories has a description longer than 93
  characters.

Piece 1 of "What it would take" has since landed, independently of this record:
agent-ops#893 (issue #888) shortened both descriptions to fit the limit, added a
`test/labels.test.sh` assertion that reads `labels_catalogue`'s own output for
every role — so a future entry cannot reintroduce it — and recorded the
100-character cap in requirement 6a as an as-built rule. Where the label is
absent outright, that is the whole fix: the next ensure sweep in
`Poetic-Poems/poetic` and `Poetic-Poems/poetic-fiddle` can now create
`open-question` successfully.

What it does not do is repair the three repositories that already carry
`obsolete` and `open-question` with empty, hand-created descriptions, because
ensure is create-only and never revisits a label that exists. Those need either
a hand PATCH or the `labels_reconcile_role` wiring that TD-PPagop-26082809
covers — wiring that would itself have inherited the same 422 had the
descriptions not been shortened first.

Piece 2 — whether the gate should read only the label — is unchanged by this
and remains the design call for whoever owns requirement 8f.
