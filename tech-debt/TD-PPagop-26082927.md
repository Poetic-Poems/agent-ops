What: `item_live_text` (lib/candidate-select.sh:611-625) resolves a `tech-debt` source item via `gh api repos/<repo>/contents/tech-debt/<item>.md`. Since #923 a tech-debt item ref is a bare issue number, so that fetch 404s for every post-migration item. Why it matters: `item_text_fault` (requirement 17g, same file ~line 696) deliberately treats a failed live-text fetch as fabricated rather than assumed-compliant, so any tech-debt candidate whose entry was trimmed by the Co-Ordinator's fit ladder is hard-skipped with `cause: "fabricated"` — a permanent, never-repaired skip — for a fetch that can no longer succeed by construction. The second caller (~line 758, requirement 17f) fails soft and merely skips its check. Where: lib/candidate-select.sh, `item_live_text`'s `tech-debt` case and its header comment (which still says a tech-debt item's live text is 'the register file's raw content'). Suggested fix: route `tech-debt` through the same `gh issue view <n> --json body,comments` path as `issues` — since #923 the band's gather entry body is the issue thread, so that is what 'matching what its own gather entry's body carries' now means — and update the function's header comment plus the requirement 17g spec text that describes the register fetch. Dedup-searched `pw::type:tech-debt` and the wider tracker for item_live_text/17g: #933 (the `:-{}` stray-brace disarm) and #830/#821 are adjacent but none covers this fetch path. Noticed while approving #949 (issue #879), which moved the conventions off the register but correctly left this read path outside its scope.

Noticed while the Approver was judging https://github.com/Poetic-Poems/agent-ops/pull/949.
