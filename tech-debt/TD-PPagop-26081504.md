Raised by the pipeline Reviewer on PR #400
([comment](https://github.com/Poetic-Poems/agent-ops/pull/400#issuecomment-5295275108)),
as a residual of that fix rather than a defect in it.

PR #400 (issue #393) split human-visibility warnings and successes into
families — `review-request`, `nudge`, `dequeue-notice`, and `generic` for a
shape the reduction does not recognise — so that succeeding at one action no
longer clears an outstanding warning from another. That is correct, and
requirement 38f's text already acknowledges the consequence recorded here
("not yet done for this one").

The consequence is that an identity's standing warning can now be cleared by
exactly two things: a later same-family success in
`human_visibility_violations` (`lib/human-visibility-hygiene.sh`,
requirement 38e), or the live re-check in
`scripts/gather-human-visibility-hygiene.sh`, which decides `keep`/`drop` by
asking GitHub whether the violation still holds. `dequeue-notice` is the only
one of the three families with no re-check class: `_warning_class` matches
`could not request review from` / `idle nudge comment` / `no legal
review-request candidate` and returns `unknown` for `could not post the
merge-queue-dequeued notice`, which then takes the `keep` fail-safe.

## Why it matters

On the common path the warning self-heals through the first mechanism, and
does so honestly: the notice's idempotence marker is checked against the pull
request's real comments, so a failed POST leaves no marker, the next sweep
pass retries, and a successful retry logs `human-dequeue-notice` — a
same-family success that clears it.

The gap is the narrow path where the retry never comes, because the notice
block is gated on `mq_queued == "false" && -n "$mq_dequeued_at"`:

- the POST fails, and the pull request is then **re-queued**. `mq_queued`
  is `true`, so no later pass retries; nothing else in either mechanism can
  clear the warning, and it stands until the pull request closes or ages out
  of the rotated log window.
- once #394/PR #422 lands, the same holds when the POST fails and the
  `dequeued_at` timestamp ages past
  `merge_queue_dequeue_notice_max_age_hours` (default 24 h) before a pass
  retries it.

A stuck warning is the fail-safe direction — it surfaces rather than hides —
but it surfaces as a `human-visibility` candidate the Co-Ordinator can select
and an implementor cannot resolve, since the condition it names is no longer
true. That is the same false-work cost the live re-check exists to remove
for the other two families.

## Where to look

- `scripts/gather-human-visibility-hygiene.sh` — `_warning_class` and
  `_pr_violation_survives`; a `dequeue-notice` class would read the pull
  request's comments for the `<!-- agent-ops:merge-queue-dequeued:<ts> -->`
  marker, exactly as the `could_not_post_nudge` class already reads for
  `agent-ops:human-nudge`. The marker is scoped to `dequeued_at`, which the
  warning's detail text does not currently carry — either widen the class to
  "any dequeue marker present" or have `sweep-human-visibility.sh` include
  `dequeued_at` in the warning detail (the `no_candidate` class already sets
  the precedent of carrying state in the detail, via `enabler_assignee=`).
- `lib/human-visibility-hygiene.sh` — `warning_family`, the authority on
  which shapes exist.
- `scripts/sweep-human-visibility.sh` — the `mq_queued == "false"` gate that
  makes the retry conditional, and the `warn` call it guards.

While there, note a smaller drift of the same kind: `warning_family` maps six
per-pull-request warning shapes, `_warning_class` only three. The two
uncovered `review-request` shapes ("could not re-request review after an
answered round", "could not tell whether the blocking review round was
answered") are less exposed, because a later `human-review-requested` does
clear them by family — but their live re-check is `keep` regardless of what
GitHub says. Whatever fix lands here should keep the two lists in step, and
ideally make the drift detectable.
