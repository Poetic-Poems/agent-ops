Noticed while working #872.

`lib/labels.sh`'s catalogue now carries `pw::type:tech-debt` as a fixed,
non-configurable name — D24's trust anchor for tech debt filed as a GitHub
issue (D15): only a collaborator with triage can apply a label, so an
issue's membership of the `tech-debt` work band is trustable even though its
body stays untrusted data. That property depends on the pipeline itself
never being the one applying the label.

`scripts/doctor.sh` already fails a config that sets a configurable label
key (`pr_label`, `enabler_escalation_label`, `needs_refinement_label`,
`refined_label`, `unvoid_label`, or `project_review`'s `pr_label`) to
`obsolete`, for exactly this reason: a stage projecting a configured label
under a reserved name would apply a human-only control itself. It has no
equivalent check for `pw::type:tech-debt`. An operator who renamed, say,
`needs_refinement_label` to `pw::type:tech-debt` would have the Co-Ordinator
project that exact label onto an issue it judged under-specified
(requirement 34e) — the pipeline applying D24's own trust anchor to an
issue nobody with triage rights ever labelled, silently defeating it.

## Suggested fix

Add `pw::type:tech-debt` to `scripts/doctor.sh`'s existing reserved-name
loop (the one currently checking only `obsolete`) alongside the other
configurable label keys, the same shape `blocked`'s own issue-side check
already uses. Regression-test it in `test/doctor.test.sh` the same way the
existing `obsolete` reservation is covered.
