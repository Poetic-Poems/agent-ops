**What.** `lib/updater-health.sh`'s `updater_status` (agent-ops#603, PR #929)
answers for the container that calls it, and both callers —
`scripts/state-sync.sh`'s heartbeat push and `scripts/publish-dashboard.sh`'s
self row — run from the crontab in the **scheduler** container. But the
`com.centurylinklabs.watchtower.lifecycle.pre-update` label sits on the shared
`x-agent-ops` block in `deploy/docker/compose.yaml`, so the hook also runs
(and on a tailnet node writes its own ledger) in the `dashboard` container,
and runs without being able to record at all in `egress-proxy`, whose state
mount is read-only.

**Why it matters.** If watchtower replaces the scheduler but collides on a
sibling — the 2026-08-14 failure was a per-container name collision, so a
partial roll is a real shape — the stuck sibling's ledger is only ever read as
*foreign*, feeding the `rolled` fallback or nothing: no heartbeat field, no
badge on any node, while that container keeps serving an image the rest of the
stack has left behind.

The 2026-08-14 incident itself is covered (both containers failed together, and
the scheduler's own ledger fires the detection), and this is one instance of an
existing shape — `version`, `compose` and `stage_health` are likewise facts
about the scheduler container published as facts about the node — which is why
it is debt rather than a defect in #929.

**Where.**

- `lib/updater-health.sh` — the foreign-ledger branch
- `scripts/state-sync.sh` and `scripts/publish-dashboard.sh` — the callers
- `deploy/docker/compose.yaml` — the shared label block
- `docs/IMPLEMENTATION-PIPELINE-SPEC.md` requirement 2.5 and
  `docs/DASHBOARD-SPEC.md` — which would need to say whose verdict the field
  carries

**Suggested fix.** Fold the worst verdict across the ledgers of *live* sibling
hostnames into the published `updater` field — but "live" is exactly the
judgement `TD-PPagop-26082913` already needs (a hostname that stopped being
polled versus one watchtower is asking and failing), so the two should be
solved together.
