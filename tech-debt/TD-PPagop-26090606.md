Since requirement 17h (agent-ops#769, PR #1187), the Script composes context/acceptance for review-feedback, merge-conflicts, dequeued and abandoned-drafts directly from the pre-fetched band entry. Under requirement 48's expensive-gather caching, that entry can be many cycles old for every repo but the one this cycle re-read. The previous prompts/coordinator.md obliged the Co-Ordinator, on a non-fresh entry, to 'write your context/acceptance from what the live read shows, never from the stale snapshot alone'; the rewritten bullet keeps the live check but only as select/don't-select — a PR that is still real but whose description was edited since gathered_at now flows into context stale, with no live correction anywhere. Mitigations that make this low-severity: PR descriptions rarely change between cycles, the fit ladder never trims these bands so the text is at least complete-as-snapshotted, and the Implementer on all four sources is handed pr_url and reads the live PR anyway. Still, the work order's context is documented (requirement 20) as the entry's body verbatim, and 'verbatim as of several days ago' is a weaker guarantee than the one the prompt used to state. Fixes: (a) extend requirement 17h's live-read path to these four sources when the entry's expensive_gather.fresh is false, mirroring item_live_entry with a gh pr view; or (b) record the acceptance of the staleness in requirement 17h/20 explicitly, so the spec states the guarantee actually made.

## Default: Option (a): live-refresh the entry's body via gh pr view before templating whenever expensive_gather.fresh is false — it reuses 17h's existing fail-closed shape and costs one gh read only for the one selected non-fresh candidate.
Noticed while the Approver was judging https://github.com/Poetic-Poems/agent-ops/pull/1187.
