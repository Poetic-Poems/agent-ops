agent-cycle.sh's claim loop exempts a requirement-17h-composed candidate from refinement_traceability_fault on the stated ground that compose_selected_candidate_text already calls refinement_traceability_repair unconditionally, 'so the splice this check exists to verify has already happened by construction'. That is not quite true for a comment_url-recorded refinement: the repair's fetch (lib/candidate-select.sh:612, `body="$(gh api ... 2>/dev/null || true)"`) swallows a failed gh read and silently skips the splice — the exact fail-open direction TD-PPagop-26082307 closed for refinement_traceability_fault's identical fetch, which the exemption now bypasses for every composed candidate. In practice the exposure is a sliver: comment_url refinements live on issues/tech-debt threads, item_live_entry's fail-closed live read already carries the whole thread into the composed context, and gh issue view's comments field caps at ~100 comments — so the refinement is lost only when the thread is long enough for the live read to miss the comment AND the repair's own gh read fails at that moment, with no fault, no guard_warn, and no retry. The spec's requirement 17h bullet ('spliced unconditionally') and the claim-loop comment ('checking it again would only ever pass') both overstate the guarantee and should be tightened alongside the fix.

## Default: Make the repair's comment_url read fail-closed when invoked from compose_selected_candidate_text — propagate the failed gh read so compose returns 1 and the candidate is skipped as untraceable, matching TD-PPagop-26082307's direction — rather than re-running the bypassed fault check after composing.
Noticed while the Approver was judging https://github.com/Poetic-Poems/agent-ops/pull/1187.
