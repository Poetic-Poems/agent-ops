agent-ops#960 captured the `setIssueFieldValue` mutation's stderr so a `mutation-failed` result carries an `error` key, but the field-resolution GraphQL read in `lib/issue-priority.sh` (the `2>/dev/null` at the query around line 279, feeding `issue_priority_field_ids`) still discards its stderr, so a `field-unresolvable` result remains a bare reason with nothing to distinguish a schema change from a network failure or a token that lost a scope — the exact silence that let #737's one-token mismatch run unseen for three days. Issue #960's thread flagged this as 'worth weighing' but explicitly out of scope for that fix, and with #960 closed and TD-PPagop-26082322 resolved, no open record tracks it. Suggested fix: mirror #960's pattern — capture the read's stderr into a local, and on the `field-unresolvable` return include an `error` key carrying the first line (always present on that reason, empty when there was no stderr), extend maybe_run_refiner's warning the same way, document it in requirement 39g, and cover it in test/refiner-priority-triage.test.sh alongside the existing mutation-failed cases. An alternative is to log the read error directly at the point of failure instead of threading it through the result shape.

## Default: Mirror #960's result-shape pattern (an `error` key on `field-unresolvable`) rather than logging at the point of failure — it keeps the library log-free and reuses the caller plumbing and test fixtures #960 already built.
Noticed while the Approver was judging https://github.com/Poetic-Poems/agent-ops/pull/1217.
