Issue #240's acceptance criterion 1 allowed the closing-keyword rule to be
enforced by "CI or the Reviewer's script-side checks". PR #256 implemented
the CI form — `.github/workflows/closing-keyword.yml` running
`scripts/check-closing-keyword.sh` with the `agent/<N>` branch anchor — but
a workflow file only guards the repository that carries it, and only
agent-ops does. For every other target repository the pipeline raises PRs
in (poetic, poetic-fiddle), an issue-sourced PR can still merge without a
closing keyword: pre-merge enforcement there is the Implementor prompt
again, and the only deterministic defence is `sweep-closed-issues.sh`'s
post-merge branch-name fallback (requirement 17c) — a backstop that closes
the issue up to an hour late, after the defect has already happened, rather
than a gate that stops it merging.

Why it matters: #240 exists because prompt-only enforcement was silently
skipped (PR #206, issue #198 open three days, selected and voided twice).
That failure shape is still fully available in two of the three
repositories the pipeline works.

Where: the pipeline side — `agent-cycle.sh` (Implementor/Reviewer stage
wrappers) and `scripts/check-closing-keyword.sh`, which already takes
`<pr-body> [<head-branch>]` and needs no change to be run script-side; the
target repos' own CI is out of this register's scope.

Suggested fix: run the existing check pipeline-side, where it covers every
target repo at once — the Script already knows the PR body and head branch
at the point it verifies the Implementor's PR (requirement 26 territory)
and again when the Reviewer hands off, so calling
`check-closing-keyword.sh` there and treating a failure as review feedback
(or refusing the handoff) makes enforcement repo-independent. Update
requirement 25a to record which layer guards which repo. Alternatively (or
additionally) vendor the workflow into the other Poetic target repos, but
that work belongs to their registers; this item covers the pipeline-side
option that needs no per-repo adoption.
