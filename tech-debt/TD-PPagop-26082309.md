Requirement 34n retires a void entry once it is both **old** and
**actioned**, and the actioned signal it assigns the `review-<date>-R-NN`
shape is `review-merged`: `scripts/gather-review-status.sh` reports a ref
`"merged"` when a merged pull request on the default branch *names that ref*.
That is the right test for requirement 16's own question — "is this
recommendation finished?" — and it is the wrong test here, because the two
questions have disjoint answers.

## What happens

A project-review recommendation becomes void when a stage finds the work
already done. The Implementer that would have closed it out, and put the ref
in its pull request body, never ran — that is precisely why the item was
voided. So no merged pull request names the ref, `gather_review_status`
reports nothing for it, `void_review_plan_actioned` returns no pair, and the
entry stays in the extract for ever.

Measured on the fleet's union log on 2026-08-23, against a 135-entry,
156,454-byte extract (the size the standing `MAX_ARG_STRLEN` warning of
agent-ops#646 names): seven entries carry this shape, none is actioned, and
the **only four entries in the whole extract already past
`void_retire_after_days`** are four of those seven —
`review-2026-07-11-R-02`, `-R-03`, `-R-04` (36, 36 and 34 days) and
`review-2026-07-21-R-01` (31 days). Every one of their void reasons says the
same thing in different words: *"fully implemented and merged in commit
e0ac584"*, *"already implemented and merged to main"*, *"already been
completed on main"* — work that landed under a commit which never carried the
ref.

The residue is small in bytes (~7 KB) and unbounded in time: it is the one
shape whose stuck entries accumulate at exactly the rate project reviews
produce voidable recommendations, with no mechanism anywhere that can ever
clear one.

## Why the existing escape hatches do not reach it

- **Requirement 34k** closes GitHub objects. A review ref names none.
- **Requirement 34l** repairs register rows. A review ref is not one.
- **Liveness** (`lib/void-liveness.sh`) needs the source's own structured
  gather; `project-review` is an on-demand reader, which is why 34n assigned
  it `review-merged` in the first place.
- **`void_config_actioned`** does reach it, via `source-dropped` — but only
  if a repo drops `project-review` from its `sources` altogether, which is a
  configuration change, not a lifecycle event.

## Suggested fix

The shape needs an actioned signal that describes the voided population
rather than the completed one. Two candidates, in preference order:

1. **Treat a review ref the review folder no longer offers as actioned.** A
   recommendation lives in a point-in-time review document that requirement
   25 never edits, so "still offered" is not a live property the way an open
   alert is — but *"the review that minted this ref is no longer the current
   one"* is readable locally and is the same argument
   `void_config_actioned`'s own rule rests on: a ref no source will offer
   again buys no suppression, so retiring it costs nothing. This is the
   analogue of liveness for a shape whose source is a document rather than a
   query.

2. **Age-only retirement for this shape specifically.** The objection
   TD-PPagop-26081303 raised against age-only retirement — that a still-
   gathered id is doing live suppression work — is the objection that does
   not apply here, for the same reason the config signal escapes it: a
   recommendation from a superseded review is never re-offered, so a wrong
   retirement cannot cause the rediscovery churn requirement 34k exists to
   stop.

Whichever lands, `docs/IMPLEMENTATION-PIPELINE-SPEC.md`'s requirement 34n
needs the new signal named alongside the six it lists, and
`test/cycle-state.test.sh`'s `void_review_plan_actioned` section extended:
today it asserts only that `"merged"` actions and anything else does not,
which is exactly the behaviour this item is about.

## Where

- `lib/void-liveness.sh` — `void_review_plan_actioned`, the function that
  can only ever answer `"merged"` for this shape.
- `scripts/gather-review-status.sh` — the reader behind it, correct for
  requirement 16's question and reused here for a different one.
- `agent-cycle.sh` — the `void_review_status_json` walk that feeds it.
- `docs/IMPLEMENTATION-PIPELINE-SPEC.md`, requirement 34n — the
  actioned-signal list.

Noticed while diagnosing agent-ops#646's standing extract-size warning: the
same measurement that showed 97% of the extract is simply younger than
`void_retire_after_days` showed that every entry which *has* aged out is of
this one shape.
