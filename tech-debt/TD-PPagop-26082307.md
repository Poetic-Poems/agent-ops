Requirement 17f (`refinement_traceability_fault`, `agent-cycle.sh`,
agent-ops#626, PR #702) decides whether a model-composed candidate's
`context`/`acceptance` really carries that item's own recorded refinement, by
testing for the refinement text **verbatim** (jq `contains`) — a `spec`
straight out of `refinements`, or the live-fetched body of the comment its
`comment_url` names. Both of its outcomes are effectively invisible:

- **A false fault costs the item its turn, quietly.** The text being matched
  against is a model's paste of a multi-kilobyte spec or issue thread.
  Ordinary paste drift — a reflowed line, a normalised list marker, a trimmed
  trailing space, a thread long enough that the model elides part of it — is
  enough to defeat `contains` on a work order that is otherwise perfectly
  correct and names the right item. So is a refinement comment *edited*
  between the cycle's own `gather-issues.sh` read (what the Co-Ordinator was
  handed and pasted) and the claim-time `gh api` re-read (what the check
  compares against). The candidate is then skipped with a `claim-skipped` /
  `cause: "untraceable"` event and nothing else — no `warning`, no counter,
  no dashboard tile. A candidate that drifts the same way every cycle
  starves indefinitely, and the log line reads identically to the genuine
  cross-item swap the requirement exists to catch.
- **A degraded `gh` read disarms the check, also quietly.** The comment fetch
  is `gh api … 2>/dev/null || true`, and an empty body returns "no fault"
  (deliberately: it fails open, the direction every other degraded `gh` read
  in this pipeline takes). But nothing is logged when it happens, so an
  expired token, a scope change or a sustained rate limit turns requirement
  17f into a permanent no-op that still reads as a passing check. Contrast
  `agent-cycle.sh`'s own `default_branch`/`commit_ts` reads, which capture
  stderr and route it through `guard_warn` precisely so a degraded read is
  visible.

## Why it matters

The requirement's whole value is that it fires rarely and means something
when it does. Neither outcome can currently be distinguished from the
healthy case without reading raw cycle logs by hand, which is exactly the
position agent-ops#626 was in before it was diagnosed — a stalled item whose
cause was invisible until a human went looking.

## Where

- `agent-cycle.sh` — `refinement_traceability_fault` (the `contains` tests
  and the `gh api` fetch), and its call site in the claim loop (the
  `claim-skipped` / `untraceable` event).
- `docs/IMPLEMENTATION-PIPELINE-SPEC.md` — requirement 17f, acceptance
  check 7g.

## Suggested fix

Two independent pieces, either useful alone:

1. Make the comparison tolerant of the drift that is not a swap — compare
   with runs of whitespace collapsed, or require a distinctive contiguous
   slice of the refinement rather than the whole of it. A cross-item swap
   (the #571/#529 shape) shares no such slice, so detection power is
   essentially unchanged while ordinary paste drift stops faulting.
2. Make both outcomes observable — log a `warning` when the comment fetch
   degrades, and surface the `untraceable` skip count where `claim-skipped`
   and the race-loss counters already surface
   (`scripts/publish-dashboard.sh`), so a rising rate is visible without
   grepping cycle logs.
