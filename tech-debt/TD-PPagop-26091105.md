Requirement 2m as rewritten by agent-ops#1279 gives the installation one push
channel (`lib/notify.sh`'s `notify_post`) and states that everything the fleet
already knows to log about an escalation, a page or a stand-down also reaches
it. Its `escalation` class is scoped, in the requirement's own words, to "every
fresh issue `create_escalation_issue` creates" — so the Pipeline Monitor
(agent-ops#1284, `docs/MONITOR-PIPELINE-SPEC.md` M14c) does not violate the
requirement as written, because it files through its own
`monitor_create_issue` rather than through `lib/enabler.sh`'s. It plainly
falls short of the requirement's stated intent: M14c's escalation is "the only
path from this pipeline to the owner", and it is the one owner-facing filing in
the system that arrives on GitHub and nowhere else.

The same is true of M14b's `pw::decision` record, which the `escalation` class
does not cover for the Enabler either, so that half is a question about the
class's scope rather than about this pipeline.

Deferred deliberately, not overlooked: agent-ops#1279 was still an open pull
request (#1327) when #1284 was specified and worked, and the work order said in
as many words not to depend on it. It landed while #1284 was in flight.

Suggested fix: source `lib/notify.sh` from `monitor-cycle.sh`, read
`notify_webhook_url`/`escalation_webhook_url`, `notify_events` and
`notify_min_interval_seconds` alongside the other configuration, and call
`notify_post escalation-filed "monitor:<finding-key>" <title> <url>
<escalation_repo> <detail> …` after a successful strategic filing — guarded by
`declare -F notify_post` the way `lib/pager.sh` guards its own calls, and
passing the run's existing union log as READ_LOG and `log.jsonl` as WRITE_LOG
so the per-(event, key) coalescing works fleet-wide. Cover it in
`test/monitor-cycle.test.sh` with a stubbed `curl` on the same PATH the `gh`
and `claude` stubs already use, asserting one POST for a filed escalation and
none when no webhook is configured. Decide at the same time whether the
`escalation` class should also carry a `pw::decision` filing, for the Enabler
and the Monitor alike; if it should, that is a change to requirement 2m's own
enumeration rather than to either caller.

Noticed while implementing agent-ops#1284, on the rebase that brought #1279's
merge into the branch.
