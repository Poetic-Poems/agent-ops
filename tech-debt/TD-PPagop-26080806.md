Requirement 34d's citation test (issue #243) recognises a cited pull request
only as `PR #N` or `pull request #N`, and a cited commit only as
`commit <sha>` or `<ref>@<sha>` — `void_evidence_cited_pr_numbers` and
`void_evidence_cited_commit_shas` in `lib/void-guard.sh`. Evidence that names
the same artefact any other way is invisible to the test, so
`void_citation_reason` finds nothing to corroborate and returns 0, and the
void is recorded on the presence test alone. Three forms that get through:

- `https://github.com/Poetic-Poems/agent-ops/pull/232`
- `https://github.com/Poetic-Poems/agent-ops/commit/aad1405b`
- `merged in #144` — a real evidence string, already a fixture in
  `test/publish-dashboard.test.sh`

The first is the form `gh pr view` and `gh pr create` both print, which makes
it the form a model is most likely to paste into `evidence`. So the gap is not
a corner: the check that exists to stop a fabricated citation is skipped by the
most idiomatic way of writing one, and the failure is silent in the direction
that costs most — a void made permanent uncorroborated, which only a human
appending `unvoided` can undo (requirement 34c).

The bare `#N` case is a separate, deliberate exclusion, documented in
`lib/void-guard.sh` above `void_evidence_cited_pr_numbers`: an evidence
sentence citing an issue is not a claim about a pull request, and treating it
as one would refuse legitimate voids on a coincidence. That reasoning stands;
this item is about the forms that unambiguously *are* pull-request and commit
citations.

Where: `lib/void-guard.sh` (`void_evidence_cited_pr_numbers`,
`void_evidence_cited_commit_shas`, `void_citation_reason`), requirement 34d
and acceptance check 8c in `docs/IMPLEMENTATION-PIPELINE-SPEC.md`, and the
three operating prompts (`prompts/coordinator.md`, `prompts/enabler.md`,
`prompts/implementor.md`), which today tell a model to cite `PR #N` without
saying that a URL is not a citation the Script can see.

Suggested fix: the extractors cannot simply gain another alternative in their
regexes, because a URL carries its own `owner/repo` and that may not be the
entry's `repo` — feeding the number straight to
`void_pr_matches_item "$repo_slug"` would test the right number against the
wrong repository and refuse a legitimate void. Have them return `slug#number`
pairs instead (defaulting to the entry's repo for the bare `PR #N` form, as
today) and have `void_citation_reason` resolve each against the slug the
citation itself names. Filed rather than fixed in PR #258 because that is a
change to the extractors' contract, not a wider pattern, and the direction
should be chosen deliberately.
