`landing_arm`'s no-queue fallback (`lib/landing.sh`, D18 WI-7, agent-ops#512)
is `gh pr merge --auto --squash`. Probes run 2026-08-18 by the maintainer
against `gh 2.96.0` (agent-ops#553) established that from
`mergeStateStatus: UNSTABLE` — every required check green, a non-required
check still running — that call merges the pull request **immediately**,
without waiting for the non-required check to finish. True auto-merge
(the `BLOCKED` path, where `gh` genuinely calls
`enablePullRequestAutoMerge`) would have waited for it.

## Why it matters

The exposed audience is a queue-less installation at `agent-merges-routine`
or above — the D18 WI-13 adopter this no-queue fallback exists for. If such
an installation relies on a non-required check finishing before a pull
request lands (a slow integration test, a preview deploy, anything gated
as non-required rather than required), `--auto` on this `gh` version does
not give it that: the merge happens as soon as the required checks are
green, the same moment `run_landing_stage`'s own `review_gate_verdict` gate
already reads `clean`.

No repository in this fleet is exposed today — every repository here carries
an active merge queue on its default branch, so `landing_arm` takes the
`enqueuePullRequest` path, never this fallback (agent-ops#553). This item
is adopter-facing documentation of a real behaviour, not a live defect.

This item states the finding only. Whether the landing stage should wait for
`UNSTABLE` to settle before landing — and if so, how — is a design decision
this item does not make.

## Where

- `lib/landing.sh` — `landing_arm`'s no-queue fallback (the `gh pr merge
  --auto --squash` call) and the file's own header, which records this
  finding alongside the CLEAN/BLOCKED behaviour (agent-ops#553).
- `docs/IMPLEMENTATION-PIPELINE-SPEC.md` requirement 8d — describes what the
  `method: auto-merge` log field does and does not promise.

## Suggested fix

Not decided here. Options a future engagement could weigh: make the
no-queue fallback poll and wait for non-required checks before calling
`gh pr merge --auto --squash`; document the caveat for D18 WI-13 adopters
without changing behaviour; or leave it, since no repository in this fleet
is exposed. Whichever is chosen should update `lib/landing.sh`'s header and
requirement 8d together, matching this repository's as-built discipline.

## Resolution

Closed as `not-debt` per the owner's decision on agent-ops#648: Option B —
document the behaviour, no change to `lib/landing.sh`.

The owner's reasoning, quoted from agent-ops#648: `landing_arm` waiting on a
non-required check would make it *stricter than GitHub itself* and stricter
than `review_gate_verdict` immediately before it in `run_landing_stage`. A
non-required check is, by definition, one the repository has already
declared does not gate merging — that declaration is what "non-required"
means. If a check matters enough to hold a merge, the fix is to mark it
required, not to have `landing_arm` second-guess the repository's own check
configuration.

The finding itself is not wrong and is not withdrawn; it simply does not
call for a code change. The content this item's "Where" section pointed at
has moved: the adopter-facing caveat now lives in `docs/ROADMAP.md`'s D18
row, alongside the "mark it required" remedy. `lib/landing.sh`'s header and
`docs/IMPLEMENTATION-PIPELINE-SPEC.md` requirement 8d already recorded the
CLEAN/BLOCKED behaviour this finding is about and are unchanged by this
resolution.
