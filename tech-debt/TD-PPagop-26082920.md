title: "`rework` events reach the dashboard's log tail as detail-less rows, and `claim-race-duplicate` can fire several times per cycle, so they displace rows an operator can act on"
status: open
filed: 2026-08-29
---

**What.** Requirement 47 (agent-ops#596) adds a `rework` event to `state_dir/log.jsonl`. `scripts/publish-dashboard.sh`'s log tail (around line 1733) filters exactly two event types out — `review-gate-checks-read` and `first-seen` — on the stated ground that they are "machine bookkeeping with nothing an operator can act on". `rework` was not considered, so it renders through the generic tail renderer, which shows each event's `detail` verbatim; the rework record carries no `detail` field, so every row renders bare.

**Why it matters.** Volume, not correctness. `claim-race-duplicate` fires once per contended candidate per cycle (`agent-cycle.sh`'s claim loop, one per `claim-lost` whose `cause` is `held`/`pr-held`), and healthy contention in a multi-node fleet is routine rather than exceptional; `stage-rerun` fires on every backstop kill. The tail is capped at `MAX_LOG_TAIL` rows, so a run of these pushes out rows that do carry an operator-actionable `detail`. The dashboard is the operator's only view of a quiet fleet, and this degrades it in exactly the "displace rows that have something to say" way requirement 33 already names for the two filtered events.

**Where.** `scripts/publish-dashboard.sh`, the `log_tail_json` filter and the comment above it; `docs/DASHBOARD-SPEC.md` and requirement 33 of `docs/IMPLEMENTATION-PIPELINE-SPEC.md` both record the reasoning for the existing exclusions and would need the same treatment for whatever is decided.

**Suggested fix.** Decide between two readings and record which. Either `rework` is bookkeeping for the Phase 2 rework panel and belongs in the same filter as `review-gate-checks-read` — one line, plus the reasoning in requirement 33 and `docs/DASHBOARD-SPEC.md` — or a repetition is something an operator should see, in which case the record needs a `detail` string built at `rework_fields` (`lib/rework.sh`) so the generic renderer has something to print, the way `issues-excluded` carries one for that same renderer. The second reading is the more useful one but is a change to the record's own shape, which `docs/FLOW-SCHEMA.md`'s stability policy classes as additive rather than breaking. Note that D23 explicitly holds a repetition to be no judgement and no failure, so whatever is shown must not read as an error row.

Noticed while reviewing https://github.com/Poetic-Poems/agent-ops/pull/941 (issue #596), which introduced the event.
