`monitor-cycle.sh` (agent-ops#1284) deliberately writes none of requirement 50's
`node-state` events (`docs/MONITOR-PIPELINE-SPEC.md` M19), so the seconds a node
spends running the Monitor are absent from `docs/FLOW-SCHEMA.md`'s per-node
timeline and from `scripts/node-time-state.sh`'s fold. The D21 question that fold
exists to answer — "more nodes, or fix something?" — is therefore answered from a
denominator that is slightly wrong on every node that runs a monitor pass, and
the gap grows with the pager trigger's own rate.

Deferred rather than fixed because the fold reconstructs one timeline per node
from two writers that already coordinate through each other's lock files
(`agent-cycle.sh` and `review-cycle.sh`, via `impl_cycle_running` /
`review_cycle_running`), and a third writer contributing a few minutes a day
risks clobbering a live `producing` span — a permanent loss — for a smaller gain
than the risk. `monitor-cycle.sh` does stand down while either sibling holds the
node (M3.2), so the unguarded window is narrow, but "narrow" is not the standard
that machinery is held to.

Suggested fix: give `monitor-cycle.sh` the same `suppress_node_state_*` discipline
`review-cycle.sh` carries — source `lib/node-time-state.sh`, log
`overhead`/`producing` transitions around the stage, suppress every transition
when either sibling's lock is live, and finalise a terminal state in `cleanup()` —
then add `monitor-log.jsonl` to the streams `scripts/node-time-state.sh` unions
before folding, and state it in M19 and in `docs/FLOW-SCHEMA.md`. The alternative,
if a third writer is judged too risky, is to leave the fold alone and publish the
Monitor's own wall-clock separately from its `monitor-stage-start`/`stage-end`
pair, which is already sufficient to reconstruct it.

Noticed while implementing agent-ops#1284 (the Pipeline Monitor).
