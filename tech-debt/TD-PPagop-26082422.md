`merge_autonomy_routine_complexity` (agent-ops#725, PR #729) makes the
routine-landing complexity ceiling configurable, and
`docs/reviews/2026-08-23-d18-stage-3-promotion.md` §1 now carries
`"merge_autonomy_routine_complexity": ["low", "medium", "high"]` for
agent-ops — and for agent-ops alone, since #402's Stage 3 row widens
complexity there only.

Requirement 26a already forces `complexity:high` onto any diff touching
concurrency/locking, security, CI/workflow machinery or shared library code.
That grade was the control keeping exactly those diffs away from automatic
landing; once the ceiling admits `high`, the protected-path list is the only
one left. The promotion document says so itself: "the protected-path gate
(belt and braces, risk register item 1) stays in force regardless."

**The gap is which paths that list actually covers.** agent-ops leaves
`merge_autonomy_protected_paths` unset, so it takes the schema default —
`.github/*`, `deploy/*`, `prompts/*`, `lib/*`, `config.schema.json`,
`config.json`, `agent-cycle.sh`, `review-cycle.sh`, `CODEOWNERS`. There is no
`scripts/*` entry. Requirement 26a's four risk categories do not map onto that
list cleanly: CI/workflow machinery is covered by `.github/*` and shared
library code by `lib/*`, but concurrency/locking and security code living
under `scripts/` is covered by neither. Among the files that leaves
unprotected:

- `scripts/detect-classifier-escapes.sh` — the independent post-hoc auditor of
  the landing classifier, and the only thing that would notice the gate
  misclassifying a landing;
- `scripts/doctor.sh` — the D18 autonomy-readiness verdict, including the
  ruleset and Approver-installation preconditions requirement 2.3b rests on;
- `scripts/autonomy-stage-report.sh` — the report the Stage promotion decision
  itself is read from;
- `scripts/publish-dashboard.sh`, `scripts/mine-merge-history.sh`.

A pull request rewriting any of these would be graded `complexity:high` by
26a, hit no protected path, and — once agent-ops sits at
`["low", "medium", "high"]` — arm and land with no human in the loop. That is
risk register item 1's own case (a pull request self-modifying the gate it is
riding through) reached by a route the belt-and-braces argument assumes is
closed.

The promotion document has already reasoned its way to the same conclusion for
the other two repositories, in the paragraph immediately above the one that
widens agent-ops: for poetic and poetic-fiddle it adds `scripts/*` to their
lists explicitly, because "`scripts/*` is unprotected under the inherited list.
That is the unsafe direction, not the safe one, and naming it here is what
closes it." The reasoning was simply not carried across to agent-ops, whose
`merge_autonomy_protected_paths` is left unset on the grounds that its schema
default already names agent-ops's own paths — true of the nine, but the nine
predate the ceiling being widenable at all.

**Suggested fix**: decide this before, not after, the Stage 3 promotion diff
lands. Either add `scripts/*` to the schema's own
`merge_autonomy_protected_paths` default (it is agent-ops's list by
construction, and `x-docs.value`, the two config tables and requirement 4f's
own enumeration of the nine paths would all need regenerating or updating with
it), or set an explicit `merge_autonomy_protected_paths` on agent-ops's
`repos[]` entry in the promotion diff alongside the complexity widening, the
way that diff already does for poetic and poetic-fiddle. If the owner instead
judges `scripts/*` acceptable to auto-land at `high`, that is a legitimate
call — but it should be recorded as an explicit choice in §3 of the promotion
document, since the document's current text reads as though the belt-and-
braces control covers a class it does not.

Noticed while reviewing PR #729, which makes the ceiling configurable but
deliberately changes no repository's configured value, so this is not a defect
in that pull request.
