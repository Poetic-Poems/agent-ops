title: A finishing-source item's void gets no live corroboration when the Enabler or the Implementor writes it
status: open
filed: 2026-08-08
---

Requirement 34d's citation test decides one item shape by its id alone, with
no fetch: `void_pr_matches_item` in `lib/void-guard.sh` returns 0 immediately
when the cited pull request number `<n>` matches an item id shaped `pr-<n>-…`.

```bash
if grep -qiE "^pr-$num-" <<<"$item" 2>/dev/null; then
  return 0
fi
```

That short-circuit is correct on its own terms — nothing ever writes the
synthetic id `pr-205-abandoned-1a2b3c4d5e6f` into PR #205's body or branch
name, so the body/branch test would otherwise refuse the one citation an
abandoned-draft, review-feedback or merge-conflict item can honestly make. The
gap is what is left once it fires on the `repos: []` call shape.

The Co-Ordinator is backstopped: `void_candidate_prs` still matches the
gathered candidate and reads that pull request's diff, so the claim is tested
after all. The Enabler and the Implementor pass `repos: []` by design
(requirement 34d's last bullet), so that test has nothing to run — and the
citation test has already returned 0 without a fetch. For this one item shape,
from those two stages, the guard performs no live check at all: only the
evidence-presence test applies, which is the state issue #243 set out to end.

Verified on PR #258's branch with a `VOID_GUARD_GH` stub that fails every
call, so any fetch would be visible in the result:

| entry | `repos` | result |
|---|---|---|
| item `pr-205-abandoned-1a2b3c4d5e6f`, evidence `"PR #205 has an empty diff against its base"` | `[]` | accepted, `gh` never invoked |
| the same entry with item `TD26051201` | `[]` | refused — *PR #205 … could not be read* |
| the same entry, candidate list carrying `pr_number: 205` | populated | refused — *… so "already done" is uncorroborated* |

The first row is reachable in ordinary operation. The Co-Ordinator selects
finishing-source items and hands them to the Implementor (requirement 27b),
and a blocked one becomes Enabler-eligible under requirement 35a, so either
stage can record a permanent void on an unexamined claim about the pull
request the item is named after. Only a human appending `unvoided` can undo
it (requirement 34c).

This is a residual gap, not a regression: before #243 those two stages had no
guard whatsoever, so the change is a strict improvement. It is filed because
the gap now sits in exactly the place the guard is advertised to cover.

Where: `lib/void-guard.sh` (`void_pr_matches_item`'s short-circuit,
`void_guard_reason`), requirement 34d and acceptance check 8c in
`docs/IMPLEMENTATION-PIPELINE-SPEC.md`, and the two call sites in
`agent-cycle.sh` (`maybe_run_enabler`'s `void` branch, and the
`impl_status == "void"` branch).

Suggested fix: the direction needs deciding rather than assuming, which is
why this is filed rather than fixed. Having the short-circuit fetch the cited
pull request's diff — the check `void_candidate_prs` already performs, but
driven from the item id instead of a gathered candidate — would corroborate
the claim from any stage with no candidate list needed. The trade-off is that
a finishing-source item whose pull request has since been closed or merged
would then fail a check it passes today, so what "already done" means for
these sources has to be settled first. The alternative is to have the Enabler
and the Implementor pass a real candidate list rather than `[]`, which keeps
the existing test but costs each stage the gathering the `[]` call shape was
introduced to avoid.
