What: lib/standdown.sh's open_composition (and the dashboard back-pressure card tooltip that mirrors it, dashboard/index.html) renders pipeline_ready_count with the fixed label 'changes-requested'. At `human`/`agent-approves` that is exact — the figure is precisely the CHANGES_REQUESTED ready PRs. But at agent-merges-routine or above the same figure also holds approved, otherwise-eligible ready PRs (this predates #946's narrowing — the old zeroed-n_human rule had the same property — and PR #1048's own tests now assert strings like '1 changes-requested' for a listing whose only counted PR is APPROVED, e.g. test/backpressure-wiring.test.sh's mixed scenario and test/fixtures/dashboard-data/backpressure-otherwise-eligible.json's '2 changes-requested' tooltip where one of the two is approved complexity:low).

Why it matters: the composition string exists so an operator can read why the cap tripped; at an elevated level it tells them N pull requests are changes-requested when some or all are approved and merely awaiting automatic landing, which points a human at the wrong queue.

Where: lib/standdown.sh's open_composition assignment; dashboard/index.html's back-pressure card tooltip; the exact-string assertions in test/backpressure-wiring.test.sh and test/dashboard-render.test.sh that would need updating in step.

Suggested fix: rename the label to something level-neutral such as 'pipeline-owed ready' (or render 'changes-requested' only below agent-merges-routine), updating the dashboard transcription, docs/IMPLEMENTATION-PIPELINE-SPEC.md's composition wording, and the exact-string test assertions together in one PR. Display-only — no counting logic changes.

Noticed while the Approver was judging https://github.com/Poetic-Poems/agent-ops/pull/1048.
