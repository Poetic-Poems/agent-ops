title: The Refiner still cannot proactively refine project-review or implementation-plan items
status: in-progress
filed: 2026-08-13
---

TD-PPagop-26080809 gave the Refiner a read path for `tech-debt` items by
folding the already-pre-fetched `repos[].tech_debt` array into
`refiner_candidate_items` (`lib/refinement.sh`, requirement 39a). That closed
one of the three gaps TD-PPagop-26080809 originally described; `project-review`
and `implementation-plan` are still never candidates, whatever
`refinement_policy` says about them, because the Script pre-fetches neither as
structured data — there is no `repos[].*` array for either the way there now
is for `tech_debt`.

This matters for the same reason the tech-debt gap did: a project-review
recommendation or an implementation-plan task can be as terse as a tech-debt
row, and today it can only ever be reported by the Co-Ordinator's own
`needs_refinement` and resolved by the Enabler's requirement 36b duty, never
by the cheap Refiner. Setting `refinement_policy["project-review"]` or
`["implementation-plan"]` to `"required"` or `"preferred"` is accepted by the
schema and shapes the Co-Ordinator's ranking, but produces no engagement to
act on it.

Suggested fix: unlike `tech-debt`, neither source has a pre-fetched array to
draw on, so this is not a one-line addition to `refiner_candidate_items` — it
needs its own read path, analogous to what the Co-Ordinator already does but
scoped down to just enough to write a specification: the current
review-cycle's recommendation files for `project-review`, and the plan
document at each repo's `implementation_plan_path` for
`implementation-plan`. Whether this needs a new gatherer script per source
(mirroring `scripts/gather-tech-debt.sh`) or one shared script covering both
is worth deciding once the shape of each source's own candidate object (its
`ref`, and whatever body the Refiner needs without a second fetch) is
settled.
