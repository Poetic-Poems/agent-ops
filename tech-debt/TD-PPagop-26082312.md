Noticed while reviewing PR #685 (requirement 8x, D18, agent-ops#578).

Requirement 8x's `landing-audit-record` is meant to be the one durable
answer to "what justified this autonomous landing", assembled at arming time
so nothing has to be reconstructed later. Two of its fields fall short of
that, in the same way: they record what the arming code already believed
rather than what it observed. Both were raised as open judgement calls on
PR #685 (comment 5382183315) and neither was treated as grounds for
refusing it; this record is so that they outlive the pull request.

## Why it matters

The value of this record is that a post-hoc auditor —
`scripts/detect-classifier-escapes.sh`, or a person after an incident — can
trust it without re-reading GitHub. A field that restates an input rather
than an observation is exactly the field an auditor cannot tell apart from
one that was checked, and the record carries no marker distinguishing the
two.

Neither is a live defect: nothing the record claims today is false. The gap
is fidelity, and it is cheapest to close while the write path is fresh.

### `head_sha` is the standing review's commit, not the head that landed

`_landing_stage_attempt` writes `head_sha` from `review_commit`
(`agent-cycle.sh:4614`), which is the `commit_id` of the Approver's standing
review, read at gate 4 (`agent-cycle.sh:4416-4424`). That is not necessarily
the commit that was actually merged. Where
`landing_protected_path_controls_ok` runs it does compare the two against a
fresh head read and refuses on a mismatch (`lib/landing.sh:525`), so on that
path they agree — but that check is tier- and level-conditional, so on the
paths it does not run the record's `head_sha` is "the commit someone
approved", not "the commit that landed", under a field name that reads as
the latter.

### The `human-veto` gate entry is a literal

`gates[]` records seven of its eight verdicts from variables that carry the
gate's actual finding, and `{gate: "human-veto", verdict: "clear"}` as a
hardcoded string (`agent-cycle.sh:4607`). The claim is sound — gate 4's
`_handoff_blocking_reviewers` refuses upstream of the arm, so a record
existing at all implies the veto cleared — but it is sound by inference from
the record's existence, not by evidence in it. It names no reviewer examined
and no review state read, so it cannot corroborate the gate ran, only that
the code reached this line.

## Where

- `agent-cycle.sh` — `_landing_stage_attempt`'s `landing-audit-record` write
  (the `--arg sha` binding and the `gates_json` literal).
- `lib/landing.sh` — `landing_protected_path_controls_ok`, which already
  reads a fresh head SHA for its own comparison.
- `docs/IMPLEMENTATION-PIPELINE-SPEC.md` — requirement 8x, which describes
  both fields.

## Suggested fix

For `head_sha`, either record the fresh head read the arm already has in
hand on the paths that take one, or keep the review's commit and rename the
field to say so (`review_commit_sha`), with the fresh head beside it where
available. Renaming is the cheaper half and removes the ambiguity on its
own.

For the veto gate, carry the evidence `_handoff_blocking_reviewers` already
computed — the blocking-reviewer list it returned (empty, on an arm) — as
the verdict's own supporting field, the way `protected-path-controls`
already names the paths it examined rather than only its verdict.

Worth deciding both at once: they are the same question about what a gate
entry in this record is for, and a convention settled for one should apply
to the other.
