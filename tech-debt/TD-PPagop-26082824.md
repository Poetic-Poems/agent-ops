title: "Two review-report call sites still resolve the fixed reviews/project-review-<date>/ layout, so a repository that configures report_directory is read from the wrong place"
status: open
filed: 2026-08-28

**What.** `project_review.defaults.report_directory` and
`project_review.repos[].report_directory` (agent-ops#761, PR #883,
`docs/REVIEW-PIPELINE-SPEC.md` R4a) make the review pipeline's report
directory a per-repository GNU `date`(1) format string, resolved through
`lib/report-directory.sh`. Three of the five places that name that directory
were converted with the key: the Reviewer-Agent's write path
(`prompts/project-reviewer.md`, via `report_dir` in its runtime input),
`review-cycle.sh`'s skip-guard (`most_recent_review_date`), and
`scripts/gather-project-review.sh`. Two were not, and still hardcode the
shipped default's layout:

- `prompts/coordinator.md` — the Co-Ordinator's **live read** of the
  `project-review` source names `reviews/project-review-YYYY-MM-DD/` and
  `gh api repos/<slug>/contents/reviews` in both places it describes that
  source. The Co-Ordinator receives no resolved directory at all: nothing in
  `lib/coordinator-input.sh`'s runtime input carries one.
- `.claude/skills/project-review/SKILL.md` (step 4, "Decide the output
  location") and `.claude/skills/project-review/references/resumability.md` —
  both scan `reviews/project-review-*/review-state.json` to find an
  interrupted review to resume.

**Why it matters.** Neither is wrong today, which is exactly why it is easy to
lose: the only repository configuring the key is `Poetic-Poems/agent-ops`,
which does not list `project-review` among its `sources`, and `poetic` and
`poetic-fiddle`, which do, are on the unchanged fallback. Both become wrong
for the first repository that combines the two.

For the Co-Ordinator that is a selection defect, not a cosmetic one:
`docs/IMPLEMENTATION-PIPELINE-SPEC.md` requirement 3y states that the live
read — not the Refiner's pre-fetched `project_review` array — is *the
authority for selection*, so a configured repository would have the gatherer
reading the configured directory while the Co-Ordinator reads `reviews/` and
selects from a stale review folder, or finds none and silently contributes no
candidates from a source the repository has enabled.

For the skill it is a lost-work defect: the report is written to the
configured directory (the prompt is explicit that the agent must never derive
a folder of its own), so the checkpoint lands there too, and the skill's own
resume scan then fails to find it. An interrupted review — the case
checkpointing exists for — starts over instead of resuming, at the cost of a
whole review's model time, and reports success either way.

**Where.**

- `prompts/coordinator.md` (the `project-review` bullet in the source list,
  and the "Project-review recommendations" section). Fixing it means
  resolving the directory per repository — the same
  `config_project_review_repos` resolution `lib/eligibility.sh` already
  performs for the Refiner pre-fetch — and passing it into the Co-Ordinator's
  runtime input (`lib/coordinator-input.sh`, requirement 4i), with the
  matching `docs/IMPLEMENTATION-PIPELINE-SPEC.md` edits to requirements 3y,
  15 and 4i. That plumbing is why it was not folded into #883.
- `.claude/skills/project-review/SKILL.md` and
  `references/resumability.md`. These are a **pinned vendored copy** of the
  upstream skill at `~/Code/claude-skills/skills/project-review`
  (`docs/REVIEW-PIPELINE-SPEC.md`, "The `project-review` skill (vendored)"),
  so the fix belongs upstream and reaches this repository as a re-vendor,
  never as a local edit. The narrow upstream change is to look for
  `review-state.json` under a directory the caller may name, defaulting to
  today's scan.

**Suggested fix.** Two independent changes, in that order — the Co-Ordinator
one closes the selection hole and can land here; the skill one needs an
upstream pull request first. Either could also be closed wholesale by a
decision to keep the report directory fixed after all, in which case #761's
key is what goes rather than these two call sites.

Noticed while reviewing PR #883 (agent-ops#761), which added the key.
