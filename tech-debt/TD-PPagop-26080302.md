Requirement 34i clears a block the cycle it can prove the work is gone, but
only for the three classes it can decide from state the cycle already holds:
an issue, a pull request, and a tech-debt register item. Two classes are
left out, and for them the old behaviour stands — the block sits on the
dashboard until the Enabler's `enabler_recheck_hours` recheck comes round,
and an Opus engagement is spent discovering that the work was finished days
ago:

- **`project-review` recommendations** (`review-<date>-R-NN`). The review
  reports live in the repository, so the Script holds nothing to compare the
  ref against, and "done" is a judgement about prose rather than a field.
- **`implementation-plan` items** (e.g. `W10-breach-handling`). Same shape:
  the plan is a file the Co-Ordinator reads for itself, and a plan item's
  completion is a tick in a document, not a status.

Both are file-backed sources whose head SHA the source-state digest already
carries (requirement 3b), so a cheap "has the file changed since the block?"
gate is available; what is missing is a way to decide *this item* is done
without reading the prose. Nothing here is a shortcut taken under time
pressure — the two classes were left out on purpose, because a wrong
clearance costs a cycle an hour — but the gap is real and worth closing when
somebody can define done for them mechanically.

Deliberately **not** on this list, and not debt: the security and
code-quality findings. `gather-findings.sh` degrades to `[]` on an API error
by design, so absence from it can never mean "fixed"; those blocks must stay
the Enabler's, and requirement 34i says so.

Fix: give each of the two sources a completion signal the Script can read —
for review recommendations, most likely the report's own status line, and
for plan items the plan's checkbox state — then extend `work_gone_clearances`
and `test/work-gone.test.sh` with a class each, in both directions.

Filed 2026-08-03, while implementing requirement 34i (#171).
