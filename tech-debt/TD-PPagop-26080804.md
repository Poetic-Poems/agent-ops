Requirement 31b's promise — the human who asked for changes is re-asked to
look once the Implementor has answered them — is kept only at the moment of
handoff (`confirm_review_requested` on the Reviewer's `ready` verdict,
`agent-cycle.sh`). If the cycle dies between the Implementor's push and that
call, or the call itself reports `failed`, the pull request sits answered,
green and in nobody's review queue until a human happens to look. The
periodic sweep (`scripts/sweep-human-visibility.sh`, requirement 38c) was the
natural place to self-heal that, and deliberately does not.

It cannot, yet, because it cannot tell that case apart from the routine one.
An unanswered round looks identical to GitHub's cheap signals —
`reviewDecision` stays `CHANGES_REQUESTED` either way, because the author can
never clear it — and re-requesting on an unanswered round does two kinds of
damage:

- a queue inversion: the pull request's next actor is the pipeline, yet it
  lands in `pulls/review-requested`, and the human opens it to find nothing
  changed since they asked;
- a silent starvation: requirement 3c's candidate rule
  (`scripts/gather-review-feedback.sh`) reads a review-requested timeline
  event as the round having been *answered* — that is the
  events-not-timestamps fix for PR #205 — so the sweep's own request would
  drop the pull request out of the Implementor's review-feedback selection
  while the human's `CHANGES_REQUESTED` sat unanswered. The exact failure
  PR #252 removed, reintroduced hourly and fleet-wide.

The discriminating predicate already exists, in the one place requirement 34a
says it may: `gather-review-feedback.sh` derives "answered" from events
GitHub itself stamps (a marked reply — a review or general comment carrying
`lib/pipeline-marker.sh`'s marker — after the blocking review's
`submitted_at`; the review-requested event is the *other* answer signal, and
the sweep must consult only the marked-reply half or it would read its own
past requests as answers).

Fix: extract the answered-from-events read into a shared library function
(say `lib/handoff.sh` or a sibling, taking the blocking review's timestamp
and answering `answered`/`unanswered`/`unknown` from the reviews, comments
and timeline reads), have `gather-review-feedback.sh` call it so the rule
keeps one definition, and have the sweep call `confirm_review_requested` only
on `answered` — `unknown` must stay a no-op, not a request. Requirement 38c's
design note and `scripts/sweep-human-visibility.sh`'s header both name this
record and need updating when it lands; `test/sweep-human-visibility.test.sh`
then wants the three-way case (answered/unanswered/unreadable) covered
against the stub.

Referenced from: PR #257 (requirement 38's sweep, where the omission is
recorded), PR #252 (the events-not-timestamps fix), issue #242.
